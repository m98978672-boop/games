# «Карман» (KARMAN) — Linux-среда на внешнем USB SSD

Дизайн-документ: возможности, архитектура, хранение, сценарии, безопасность, MVP.
Реализация лаунчера описана в [`README.md`](./README.md) этого раздела; здесь — только проект, без кода.

> ⚠️ **Главное предупреждение, до всего остального.**
> По требованию пароля и шифрования нет. Это значит: **любой, кто возьмёт накопитель в руки, прочитает всё его содержимое** — рабочие файлы, историю браузера, ключи SSH, если вы их туда положите, журналы сессий. Достаточно вставить SSD в любой ПК или телефон: ничего взламывать не нужно.
> Никакая «карманность» это не компенсирует: защита только физическая — не терять, не оставлять без присмотра, не давать чужим. Если накопитель уйдёт — считайте данные раскрытыми. Восстановить/стереть удалённое тоже не получится гарантированно.
> Ниже в разделе 5 разобрано, что можно сделать без шифрования, и к чему приведёт отказ от него.

## 1. Что возможно, что невозможно и какие есть ограничения

### 1.1 Общая реальность

Linux-среда «на флешке» — это не одна технология, а три принципиально разных варианта, и они дают **разный Linux**:

| Вариант | Что происходит | Своё ядро? | Нужен драйвер/права? | Скорость |
|---------|----------------|-----------|----------------------|----------|
| **Полная виртуальная машина** (QEMU/WSL2) | На хосте запускается эмулятор/гипервизор, внутри грузится настоящее ядро Linux | да | QEMU — нет; WSL2 — функция Windows (разовая установка, админ) | 30–90 % от нативной |
| **Пользовательское окружение** (proot / контейнер) | Программы Linux работают в userspace поверх **ядра хоста** (Android/Termux, proot-distro) | нет | приложение + разрешения | 40–80 %, отдельные системные вызовы недоступны |
| **Загрузка с накопителя** (Ventoy / live) | ПК грузится прямо с SSD, хост не нужен | да | доступ к BIOS/UEFI | 100 % |

Ключевой вывод: **«одинаково на всех устройствах» не бывает**. На Windows вы получаете полноценный Linux в виртуальной машине; на Android — userspace-окружение без своего ядра; на «голом железе» — загрузку с SSD. Обещать единый опыт нельзя, можно обещать **одни и те же данные и одинаковый способ их хранения**.

### 1.2 Windows — что реально работает

**Работает без прав администратора:**
- портативный **QEMU** (`qemu-system-x86_64.exe`), образ системы и оверлей лежат на SSD, в систему ничего не устанавливается;
- при включённой функции Windows Hypervisor Platform ускорение WHPX (близко к нативной скорости), иначе — программная эмуляция TCG (медленно: загрузка 1–3 мин, интерактив терпимый для текста, плохо для видео);
- сеть через NAT QEMU (`-netdev user`) — интернет предоставляет хост, гостю отдельный доступ не нужен.

**Работает, но требует разовой подготовки (админ + виртуализация в BIOS):**
- **WSL2**: `wsl --import` дистрибутива из образа, каталог дистрибутива размещается **на SSD**. Даёт почти нативную скорость и прозрачный доступ к файлам SSD через `/mnt/e/...`. Ограничения: Windows 10 2004+ / 11, включённая виртуализация, разовая установка компонента (нужен админ и перезагрузка), VHDX не любит exFAT и не прощает извлечения на ходу. Поэтому WSL-режим — **опция**, а не база.

**Работает, если разрешает железо:**
- загрузка с SSD (Ventoy) — единственный способ получить «настоящий ПК в кармане», но нужен доступ к Boot Menu / отключение Secure Boot; на корпоративных ПК часто запаролено.

**Не работает / не обещаем:**
- «просто вставил — Linux сам запустился». Автозапуск программ с USB в Windows 7+ отключён политикой; пользователь запускает `.cmd`-файл вручную. Обходить это мы не будем — это ровно тот механизм, которым распространяется малварь;
- проброс физического SSD внутрь виртуальной машины (raw-доступ к диску требует администратора и рискует целостностью);
- работа с ext4-разделами SSD из Windows без сторонних драйверов.

### 1.3 Android — что реально работает и где стена

**Работает (с приложением-компаньоном и явными разрешениями):**
- **Termux + proot-distro** (или собственное приложение со встроенным proot): Debian/Ubuntu в userspace, `apt`, компиляторы, Python, SSH-клиент — без root;
- доступ к файлам на SSD через **SAF** (`~/storage/external-1`): чтение/запись обычных файлов;
- проброс сети от телефона (Wi-Fi/LTE) — сам собой, гость использует сеть приложения.

**Стена №1 — исполнение файлов с SSD.** Внешний накопитель на Android монтируется через FUSE/SAF: нет POSIX-прав, нет симлинков, **нет разрешения на исполнение**. Значит rootfs Linux нельзя «жить» на SSD и запускаться оттуда. Он должен лежать в приватном каталоге приложения (внутренняя память), а SSD — хранить **данные, образ rootfs для развёртывания и контрольные точки**. Это не недоделка, а ограничение платформы.

**Стена №2 — нет виртуализации.** KVM на телефоне недоступен без root и без поддержки ядра; полноценная VM (как на Windows) — невозможна легальным путём. proot — не виртуалка: это подмена путей и системных вызовов, ядро общее с Android.

**Стена №3 — разметка и питание.** Многие телефоны видят **только первый раздел** внешнего накопителя, поэтому многораздельная схема на Android ненадёжна. Автономный SSD может не запуститься от OTG-порта (лимит тока) — нужен Y-кабель или хаб с питанием. Файловая система: exFAT читается большинством устройств, NTFS — не всеми, ext4 — только с root.

**Стена №4 — фон и батарея.** Android агрессивно выгружает фоновые процессы: длительные сборки/серверы в proot будут прерываться без wakelock и отключения оптимизации батареи.

### 1.4 Разница «VM» и «среда без виртуализации» — коротко

- **VM (Windows/QEMU, WSL2):** своё ядро, свои драйверы, `systemd`, mount, сеть — всё по-настоящему. Цена: скорость, вес образа, необходимость гипервизора.
- **proot/контейнер (Android):** общее ядро, нет `mount`, ограничены `ptrace`/`namespaces`, часть пакетов не работает; зато нет root, нет образа в десятки гигабайт и запускается на любом телефоне.
- Обе схемы работают с **одними и теми же файлами** в `data/`, если не использовать в них POSIX-специфику (права, симлинки, регистрозависимые имена, длинные пути).

## 2. Рекомендуемая архитектура

### 2.1 Windows

```
┌──────────────────────────── USB SSD (exFAT) ─────────────────────────────┐
│  ЗАПУСТИТЬ-КАРМАН.cmd ──► karman/launcher/karman-launcher.ps1            │
│                              │                                            │
│                              ├─(есть WSL2 + режим wsl)──► wsl.exe         │
│                              └─(иначе)──► karman/engine/qemu/*.exe        │
│  karman/system/base.qcow2  (система, только чтение)                       │
│  karman/state/overlay.qcow2 (все изменения сессии)                        │
│  karman/checkpoints/*.qcow2 (контрольные точки)                           │
│  data/                      (общие файлы, видны и без Linux)              │
└───────────────────────────────────────────────────────────────────────────┘
        на хосте НЕ устанавливается ничего (QEMU-режим)
```

Два движка, автовыбор, явный откат:
- **QEMU** — базовый, работает без админа на любом ПК с Windows 10/11 x64. Гость получает сеть через NAT, `data/` подключается как FAT-диск (по умолчанию **только чтение** — так безопаснее; запись включается отдельным флагом с предупреждением).
- **WSL2** — ускоренный, если компонент включён; `data/` доступен через `/mnt/<буква>/data` без всяких прослоек.

### 2.2 Android

```
┌──── Android ────┐        ┌──────── USB SSD (exFAT) ────────┐
│ приложение-     │  SAF   │ data/            (общие файлы)  │
│ компаньон       │◄──────►│ rootfs/debian.tar (образ среды)│
│ (Termux/своё)   │        │ checkpoints/     (копии данных)│
│                 │        │ karman/manifest.json           │
│ /data/data/...  │        └────────────────────────────────┘
│  rootfs + proot │
└─────────────────┘
```

- rootfs распаковывается **во внутреннюю память приложения** (иначе нет исполнения);
- `data/` на SSD читается/пишется через SAF; при старте — «импорт» изменений, при завершении — «экспорт» + контрольная точка;
- приложение **не** получает доступ к внутренней памяти телефона по умолчанию: только папка приложения и — после отдельного разрешения пользователя — выбранные каталоги/накопитель;
- что пользователь ставит на телефон: приложение-компаньон (или Termux + proot-distro) — это **не данные**, это программа; на SSD ничего не «устанавливается».

### 2.3 Общие принципы

1. **Накопитель — единственный источник истины.** Ничего важного не остаётся только в памяти хоста.
2. **Хост — временный ресурс.** Не трогаем его диск, не ставим службы, не оставляем автозапуска.
3. **Всё явно.** Один кликабельный файл запуска, журналы на SSD, никакой маскировки процессов и устройства.
4. **Разделение слоёв.** Система (base) — только чтение, изменения — в оверлее, данные — отдельно. Это то, что делает возможными контрольные точки и восстановление.

## 3. Схема хранения на USB SSD

### 3.1 Раскладка

```
<USB SSD>/
├─ ЗАПУСТИТЬ-КАРМАН.cmd        ← единственный кликабельный файл (Windows)
├─ ЗАПУСТИТЬ-КАРМАН.sh         ← он же для Linux-хоста
├─ KARMAN-ЧИТАЙ-МЕНЯ.txt       ← что это, что делает, что ему нужно
├─ data/                        ← ОБЩИЕ ФАЙЛЫ: документы, фото, проекты
│   ├─ public/                  ← можно показывать/носить без опаски
│   └─ private/                 ← паспорт, ключи, переписка — только под контролем
└─ karman/
    ├─ manifest.json            ← версия раскладки, пути, хэш образа, политика точек
    ├─ launcher/                ← скрипты запуска (это и есть «программа-помощник»)
    ├─ engine/qemu/             ← портативный QEMU (кладёт пользователь, не входит)
    ├─ system/base.qcow2        ← система Linux (только чтение на запись не открываем)
    ├─ state/overlay.qcow2      ← все изменения; пересоздаётся при сбросе
    ├─ checkpoints/<дата>/      ← копии оверлея и метаданные
    ├─ logs/session-*.log       ← журналы: когда, на каком ПК, чем закончилось
    └─ recovery/                ← инструкция и утилиты восстановления
```

### 3.2 Файловая система и разметка

| Схема | Плюсы | Минусы |
|-------|-------|--------|
| **A. Один раздел exFAT** (рекомендуется для MVP) | виден на Windows, Linux, Android, macOS (r/o), без прав; файлы > 4 ГБ | нет POSIX-прав и симлинков; WSL-режим недоступен; нет журналирования |
| B. Два раздела: NTFS (движок+образ) + exFAT (`data/`) | возможен WSL2, лучше целостность | Android часто видит только первый раздел; macOS NTFS — только r/o |
| C. Один раздел ext4 | права и симлинки, ближе к «настоящему Linux» | Windows и Android не читают без драйверов/прав |

Почему не «одна большая ext4»: тогда на Windows без сторонних драйверов не видно вообще ничего, и вся идея «одни файлы на всех устройствах» рассыпается. Поэтому **данные — exFAT, система — образ внутри exFAT**.

### 3.3 Почему base + overlay, а не один образ

- `base.qcow2` — эталон системы; при экспериментах его не жалко, он восстанавливается пересозданием оверлея;
- `state/overlay.qcow2` — только изменения; весит мегабайты, копируется за секунды → **контрольная точка = копия оверлея**, а не 40 ГБ;
- «сброс к заводскому состоянию» = удалить оверлей, данные в `data/` не трогаются.

### 3.4 Что где лежит — и что является программой

| Объект | Где | Это данные или программа? |
|--------|-----|---------------------------|
| Документы, фото, проекты | `data/` на SSD | данные (на накопителе) |
| Настройки Linux-среды | `state/overlay.qcow2` на SSD | данные (на накопителе) |
| Система Linux | `system/base.qcow2` на SSD | данные-образ (на накопителе) |
| Скрипты запуска | `karman/launcher/` на SSD | программа, но **переносимая**: не устанавливается в систему |
| QEMU | `karman/engine/qemu/` на SSD | программа, портативная, ставится копированием |
| WSL2-компонент | система Windows | **устанавливается на устройство**, требует админа |
| Приложение-компаньон | телефон | **устанавливается на устройство** |
| Termux + proot | телефон | **устанавливается на устройство** |

## 4. Сценарий: подключение, запуск, работа, завершение, извлечение

### 4.1 Нормальный цикл (Windows)

1. **Подключение.** Пользователь вставляет SSD. Windows показывает диск. Ничего не запускается само — это осознанное решение.
2. **Запуск.** Двойной клик по `ЗАПУСТИТЬ-КАРМАН.cmd` (он же «приложение» — единственный файл, который нужно найти). Появляется меню: запустить / контрольная точка / проверить целостность / безопасно извлечь.
3. **Проверки перед стартом** (все видны в консоли):
   - читается `manifest.json`, версия раскладки поддерживается;
   - на месте QEMU (или выбран WSL-режим и он доступен);
   - образ `system/base.qcow2` на месте, размер/хэш совпадает с манифестом;
   - на SSD есть свободное место под оверлей и точку;
   - нет флага «прошлая сессия не завершилась»;
   - доступен каталог `data/`.
4. **Старт.** При необходимости создаётся оверлей; пишется `state/session.lock` (время, имя ПК, режим) и первая строка журнала. Запускается QEMU, открывается окно Linux.
5. **Работа.** Файлы пишутся в `data/` (только чтение по умолчанию) и в оверлей. Хост больше ничем не занят.
6. **Завершение.** Пользователь выключает Linux **изнутри** (это важно: синхронизация ФС). Лаунчер дожидается выхода процесса, проверяет код возврата, снимает блокировку, дописывает журнал, предлагает контрольную точку.
7. **Извлечение.** «Безопасно извлечь»: сброс кэшей записи и штатное отключение тома. Только после этого физически вынимать.

### 4.2 Аварийный сценарий

- Питание пропало / выдернули кабель / закрыли ноутбук: `session.lock` остаётся.
- При следующем запуске лаунчер **честно сообщает**: «сессия завершилась аварийно; изменения после последней контрольной точки могут быть потеряны; файловая система образа может требовать проверки».
- Предлагается: (а) продолжить с текущим оверлеем (обычно работает), (б) восстановить последнюю контрольную точку, (в) сбросить систему к `base` (данные в `data/` не трогаются).
- Перед любым восстановлением текущий оверлей **сохраняется** в `checkpoints/pre-restore-<дата>`, чтобы восстановление не стало второй потерей.
- **Мы не обещаем откат на 100 %**: часть файлов в `data/` могла быть не дописана, часть — записана наполовину. Восстановление ограничено содержимым SSD и последними точками; внутренний диск хоста не затрагивается вообще.

### 4.3 Android-цикл (коротко)

Подключение по OTG → выдать разрешение на накопитель → приложение проверяет `manifest.json` → импорт `data/` (или работа напрямую через SAF) → сессия в proot → по завершении экспорт + контрольная точка → «отключить накопитель» в приложении → отсоединить.

## 5. Модель безопасности и риски

### 5.1 Базовая модель

- **Нет шифрования и пароля** → конфиденциальность обеспечивается только физическим контролем. Модель угроз: «накопитель может попасть в чужие руки», и в этом случае защита отсутствует.
- **Нет скрытности**: устройство видно ОС как обычный накопитель, процессы не маскируются, журналы пишутся и не удаляются.
- **Хост — чужой по умолчанию**: лаунчер не читает внутренний диск, не ставит служб, не включает автозапуск, не запрашивает админ.
- **Явное согласие**: на ПК программу запускает человек; на Android приложение устанавливает и разрешения выдаёт человек.

### 5.2 Риски и что с ними делать (без шифрования)

| Риск | Последствие | Мера в рамках требований |
|------|-------------|--------------------------|
| Потеря/кража SSD | полное раскрытие данных | не хранить секреты; `data/private` держать пустым или отдельно; по возможности носить два носителя: «рабочий» и «чистый» |
| Чужой/заражённый ПК | хост читает файлы, перехватывает ввод в VM, может изменить образ | работать на доверенных ПК; проверка хэша образа перед стартом покажет подмену; `data/` подключать только для чтения |
| Подмена лаунчера на SSD | выполнение чужого кода при запуске | лаунчер сверяет свои файлы и образ с хэшами из `manifest.json`; несовпадение — отказ |
| Полузаписанные файлы при выдёргивании | порча отдельных документов | штатное завершение, контрольные точки, явное предупреждение; файлы `data/` — копировать важное отдельно |
| Android: разрешения приложения | доступ шире, чем нужно | доступ только к выбранному накопителю; внутренняя память — по отдельному разрешению |
| Журналы как источник утечки | видно, где и когда использовался SSD | это осознанный компромисс: журналы нужны для восстановления и разбора сбоев |
| «Удалить навсегда» | следы остаются на носителе | честно: без шифрования надёжного стирания не гарантировать |

### 5.3 Что изменится, если передумать насчёт шифрования

Единственная мера, которая реально закрывает риск кражи, — шифрование контейнера (LUKS/Veracrypt) с паролем. Цена: пароль при каждом старте, сложность с Android (шифрованный контейнер в userspace — медленно), и «забыл пароль = потерял всё». Это отдельное продуктовое решение, а не «галочка».

### 5.4 Чего в продукте не будет

Скрытия USB-устройства от ОС, подмены его типа, обхода защит, маскировки процессов, скрытого автозапуска, постоянных фоновых служб, удаления журналов, установки без согласия, работы с внутренним диском хоста по умолчанию.

## 7. План MVP и тесты

### 7.1 Этапы

| Этап | Результат | Критерий готовности |
|------|-----------|---------------------|
| **M0. Раскладка и манифест** | SSD размечен, дерево каталогов создано, `manifest.json` с версией и хэшами | `prepare` создаёт структуру на чистом носителе; повторный запуск не ломает данные |
| **M1. Лаунчер Windows (QEMU)** | один кликабельный файл: проверки → запуск → ожидание → журнал → извлечение | запуск на 3 разных ПК Win10/11; без админа; отказ при отсутствии QEMU/образа с понятным текстом |
| **M2. Целостность и точки** | проверка хэша образа, контрольные точки, восстановление, сброс к base | подмена образа обнаруживается; восстановление не теряет `data/`; «pre-restore» создаётся всегда |
| **M3. Android-компаньон** | приложение: разрешение на накопитель, SAF-доступ, proot-сессия, импорт/экспорт | на 3 телефонах: видит SSD, читает/пишет `data/`, сессия не рвётся 30 мин |
| **M4. Linux-хост и второй движок** | `ЗАПУСТИТЬ-КАРМАН.sh`, опция WSL2 | запуск на Linux-хосте; WSL-режим не мешает QEMU-режиму |
| **M5. Полировка** | меню, локализация, документация, восстановление после сбоя | новичок проходит путь «вставил → запустил → вышел → извлёк» по README без вопросов |

### 7.2 Что уже сделано в этом разделе

Реализованы M0, M1 (каркас) и M2 (проверки/точки) для Windows и Linux-хоста, плюс инструменты раскладки и проверки. Android-компаньон — следующий этап, его требует отдельное приложение.

### 7.3 Список тестов

**Раскладка и манифест (автотесты, уже есть)**
1. подготовка на пустом носителе создаёт ожидаемое дерево;
2. манифест содержит версию, пути, режим проверки;
3. повторная подготовка не затирает `data/` без явного флага;
4. отсутствие обязательного файла обнаруживается проверкой.

**Целостность**
5. изменённый байт в образе → отказ запуска с указанием файла;
6. отсутствующий образ → понятная инструкция, а не трейсбек;
7. несовпадение версии раскладки → предупреждение и отказ от несовместимых действий.

**Сессии и восстановление**
8. штатный выход снимает блокировку и пишет журнал;
9. убитый процесс оставляет блокировку, следующий запуск её видит;
10. восстановление из точки создаёт резервную копию текущего состояния;
11. сброс к base не изменяет `data/`;
12. заполненный SSD → отказ старта без создания точки, без «наполовину созданных» файлов.

**Безопасность**
13. лаунчер не пишет за пределы каталога `karman/` и `data/`;
14. путь из манифеста с `..` отклоняется;
15. работа без прав администратора (проверка через непривилегированную учётку);
16. отсутствие созданных служб, задач планировщика и записей автозапуска после сессии.

**Пользовательские сценарии**
17. три разных ПК Windows (домашний, рабочий с ограничениями, без виртуализации) — запуск и работа;
18. извлечение без завершения → предупреждение при следующем старте;
19. Android: телефон с OTG + SSD на 1 ТБ (питание достаточно) и слот без питания (ожидаемый отказ с объяснением);
20. чтение `data/`, записанных из Linux, на Windows и Android (имена, юникод, длинные пути).

**Производительность**
21. время старта: QEMU/WHPX, QEMU/TCG, proot — замер и фиксация в README;
22. скорость чтения/записи `data/` на USB 3.0/3.2 и на USB 2.0 (последний — «работать можно, но больно»).

## Приложение: ближайшие безопасные варианты для невыполнимых требований

| Требование | Почему невыполнимо | Ближайший безопасный вариант |
|------------|--------------------|------------------------------|
| Linux одинаково на всех устройствах | разные механизмы: VM / userspace / загрузка | один набор данных и одинаковый способ хранения; разный рантайм — честно документирован |
| Полноценная VM на Android | нет KVM без root | proot-окружение + явные ограничения в интерфейсе |
| Автозапуск при вставке | ОС блокирует, и правильно | один кликабельный файл + меню; ровно один двойной клик |
| 100 % восстановление после выдёргивания | нет журналирования на exFAT, кэши записи | контрольные точки + честное предупреждение о потере последних изменений |
| Скрытый запуск/невидимые процессы | противоречит требованиям и природе малвари | всё видимо: окно консоли, журнал на SSD |
