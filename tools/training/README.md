# Обучение модели: знания репозитория, поиск багов, проверка игр

Здесь лежит настоящий обучающий пайплайн: он собирает знания из репозитория,
учит на них LoRA-адаптер и измеряет результат — сколько багов модель находит
и как часто ошибается на чистом коде.

Ничего не имитируется: данные — реальные файлы, метрики — на отложенной
выборке, ответы командира проверяются тем же валидатором, что и в игре.

## Где сама модель

Модель уже существовала до этой задачи — в двух местах:

| Где | Что | Размер |
|---|---|---|
| GitHub release `frontline-qwen35-0.8b-0ec1389` | `Qwen3.5-0.8B-q4f16_1-MLC.zip` + `.sha256` | 447 189 776 байт |
| Dropbox `/Запросы файлов/Frontline-Model-inbox/` | `Qwen3.5-0.8B-q4f16_1-MLC Максим.zip` | 447 189 776 байт, тот же архив |
| GitHub release `frontline-qwen35-lora-research-*` | обученный ранее LoRA-адаптер | 1 201 212 байт |

Это **перепаковка Apache-2.0 кванта** `mlc-ai/Qwen3.5-0.8B-q4f16_1-MLC`
(ревизия `0ec1389…`). Модель не «командир, проверенный в бою»: она умеет
отвечать на входы командира, но её никто не проверял на победы в войнах.

**Где не хватает доступа.** Песочница, в которой писалась эта работа, не
может скачать ни Dropbox, ни архив релиза, ни веса с huggingface.co — все три
хоста закрыты (`HTTP 000`). PyPI открыт, поэтому обучение проверено локально
на крошечной модели (`tools/training`), а полноценное обучение идёт в
GitHub Actions, где сеть открыта.

## Как учить

```bash
# 1. Собрать знания из репозитория (это делает CI и облако)
node tools/training/build-knowledge.mjs --out knowledge \
  --game 900 --bug 400 --code 40 --play 60 --readme 20 \
  --codes 1200 --law 40 --defect 40 --balance 30 --edge 40 --engine 30

# 2. Проверить данные: нет дублей, ответы принимает игра, есть «как играть»
node tools/training/test-build-knowledge.mjs

# 3. Обучить LoRA (нужны torch, transformers, peft)
python tools/training/finetune.py --data knowledge --out model-out --steps 1040

# 4. Собрать бенчмарк «найди баг» на настоящих файлах с известными дефектами
node tools/training/make-bug-bench.mjs --out bug-bench

# 5. Измерить, находит ли модель баги
python tools/training/eval-bugs.py --bench bug-bench \
  --adapter model-out/adapter --out bug-eval.json
```

В облаке всё это делает воркфлоу **Games model — обучение и проверка**
(`.github/workflows/games-model-training.yml`): кнопка Run workflow, шаги
настраиваются, готовый адаптер и отчёты выкладываются артефактом.

## Что попадает в обучение

| Тип | Откуда | Сколько |
|---|---|---|
| `game-decision` | живые бои Frontline: снимок, который видит командир, и допустимое действие | **900** |
| `game-edge` | граничные ситуации по правилам игры (порог 70%, инженер, индексы) — проверены `validateProposal` | 12 |
| `game-rule` | правила решений словами: почему supply раньше стройки | 10 |
| `bug-code` | таблица 1000 кодов баг-искателя: 920 содержательных проверок | 920 |
| `bug-code-reverse` | обратная задача: по описанию найти код | 120 |
| `bug-code-section` | границы разделов 000–900 и сколько в них проверок | 10 |
| `bug-rule` | каталог правил баг-искателя, 32 раздела | 115 |
| `bug-severity` | уровни опасности: критично / важно / мелочь | 10 |
| `defect-analysis` | разбор реальных дефектов: причина → последствие → решение | 13 |
| `balance` | числа баланса и следствия: почему пулемёт давит, танк дорог | 13 |
| `engine-arch` | устройство игры: три уровня ИИ, координаты, пороги приёмки | 13 |
| `repo-law` | законы репозитория с историей (`dawn.exr`, `stratum`, `info_hash`) | 14 |
| `play-guide` | разделы «Как играть» из настоящих README игр, без обрывов на границе предложения | 29 |
| `play-frontline` | правила и смысл Frontline из `docs/GDD.md` и кода | 7 |
| `code-bench-broken` | настоящий файл с внесённым дефектом, ответ — код и объяснение | 15 |
| `code-bench-clean` | тот же участок без дефекта, правильный ответ `{"bug":false}` | 12 |
| `code-defect` | дефекты, найденные ботом в живом коде, с фрагментом и починкой | 9 |
| `code-clean` | чистые функции для отрицательных примеров | 2 |
| `code-*` | реальные исправления: NaN в цикле, alert, пути, безопасность | 6 |
| `repo-rule` | правила репозитория: статический сайт, порядок скриптов, сохранения | 5 |

Итого **1588 примеров** (1429 обучение / 159 проверка), 24 типа.

Доля игровых примеров — **58%**, кодов багов — **25%**, примеров про код — **2.7%**.
Коды специально ограничены: это словарь, он не должен вытеснять сами задачи.

Длинные руководства режутся по границе предложения и идут частями
(«Продолжи руководство»), поэтому ничего не теряется и модель не учится
обрывать ответ. Максимальная длина примера — 938 токенов при бюджете 1024.

Каждый пример — `{system, user, assistant, kind, source}`. У каждого указан
источник: по нему видно, что модель не выдумывает, а учится на файлах.

**Почему боевые примеры честные.** Проходя полный бой (120 секунд игрового
времени), сборщик снимает состояния с обеих сторон, строит допустимое
действие и **проверяет его игровым `validateProposal`**. Если действие не
проходит валидатор, пример отбрасывается. Поэтому ответы, которые выучит
модель, игра принимает — это проверяет отдельный тест (14 тестов сборщика).

**Почему действия сбалансированы.** Если обрывать сбор по лимиту, в выборку
попадут только первые секунды боя: действия `supply` не будет вообще, и
модель его не выучит. Сборщик копит пул за полный бой и потом берёт действия
по кругу из корзин — `supply`, `hold`, `build` поровну.

## Как измеряется «находит баги»

`make-bug-bench.mjs` берёт настоящие файлы (`road-tycoon/src/sim.js`,
`folder-os/index.html`, `night-taxi/index.html`, `site/community-games.json`…)
и вносит в них известные дефекты — ровно те, что ищет бот-багоискатель:

* пропущена скобка → скрипт не загружается;
* убрана проверка `Number.isFinite(dt)` → NaN попадает в состояние игры;
* добавлен `alert()` → игра встаёт и перекрывает экран;
* ссылка ведёт на несуществующий файл;
* обратные слэши в пути;
* `new Function(...)` на строке из данных;
* висячая запятая в JSON;
* повторяющийся `id`.

К каждому дефекту кладётся **чистая копия того же файла**. Поэтому считается
не только полнота, но и ложные тревоги: модель, которая всегда говорит
«есть баг», получает полноту 100% и проваливает точность.

Метрики: `accuracy`, `recall`, `falseAlarmRate`, `unparsed` (не разобрали
ответ — это отдельная величина, а не «нет бага»).

## Ограничения, которые нельзя забывать

* На выходе **PEFT-адаптер**, а не готовая браузерная модель. Для WebLLM его
  нужно конвертировать и отдельно проверять.
* 0.8B-модель — не эксперт по коду. Она выучит формат, стиль и частые
  закономерности; сложные баги всё равно ловит бот-багоискатель.
* Обучение на 2 CPU идёт медленно: в облаке шаг ≈ 8-10 секунд, 256 шагов —
  около 40 минут. Больше шагов — дольше; рабочий лимит job — 6 часов.
* Если потеря на отложенной выборке не уменьшилась, обучение считается
  неудачным: воркфлоу на этом падает и не публикует релиз.

## Что улучшено во второй итерации

Три настоящих слабых места, найденных проверкой, а не на глаз:

**1. Обучение и оценка расходились.** Модель училась отвечать
`{"bug":true,"code":"600","why":"..."}`, а `eval-bugs.py` ждал голый
`{"bug":true}`. Метрики мерили не то, чему учили. Теперь промпт живёт в одном
файле `prompts.json`, его читают и сборщик, и оценка; рассинхронизацию ловит
тест (`обучение читает промпт из prompts.json`, `оценка читает...`).

**2. Примеров про поиск багов было 9 из 2200.** Именно это измеряет бенчмарк,
и именно этому модель почти не училась. Добавлено три источника: пары
«сломано / чисто» из бенчмарка (27), дефекты в живом коде с фрагментом (9) и
чистые функции для отрицательных примеров (2). Бенчмарк расширен с 8 до 15
дефектов: `localStorage` без try, пустой `catch`, пропавшее поле JSON,
самозакрывающийся `<script>`, промис без обработки, жёсткий порт,
функция без `return`.

**3. Порча файла могла «не примениться» молча.** Два сценария бенчмарка были
ложными: регулярка не совпадала, файл не менялся, а случай считался битым.
Теперь бенчмарк пропускает сценарий, если файл не изменился или изменился
больше чем на 10%, а тест `каждый дефект реально меняет файл` и
`каждый дефект точечный, файл не разрушен` это закрепляют.

Плюс две вещи по качеству данных:

* **Отрицательные примеры обязательны.** Без чистых фрагментов модель учится
  кричать «баг» на любой код: полнота 100% при точности около нуля. Тесты
  требуют наличия и битых, и чистых примеров.
* **Ответ всегда с фрагментом и кодом.** Обучение требует указывать место и
  правило, а не «где-то есть проблема» — так ответ проверяем.

## Как воспроизвести проверку обучения без huggingface

Веса Qwen в песочнице недоступны, но код обучения проверяется на любой
локальной модели. Проверка целиком — примерно 5 минут:

```bash
python -m venv /tmp/venv
/tmp/venv/bin/pip install torch transformers peft accelerate safetensors tokenizers numpy

# крошечная модель с нуля на данных репозитория (словарь байтового уровня,
# чтобы русский текст не терялся)
/tmp/venv/bin/python - <<'PY'
from tokenizers import Tokenizer, models, pre_tokenizers, decoders, trainers
from transformers import PreTrainedTokenizerFast, GPT2Config, GPT2LMHeadModel
import json, os
texts = []
for f in ('tools/training/dataset/train.jsonl', 'tools/training/dataset/eval.jsonl'):
    for line in open(f):
        r = json.loads(line)
        texts.append(r['system'] + '\n' + r['user'] + '\n' + r['assistant'])
tok = Tokenizer(models.BPE(unk_token=None))
tok.pre_tokenizer = pre_tokenizers.ByteLevel(add_prefix_space=False)
tok.decoder = decoders.ByteLevel()
tok.train_from_iterator(texts, trainers.BpeTrainer(
    vocab_size=3000, show_progress=False,
    initial_alphabet=pre_tokenizers.ByteLevel.alphabet()))
fast = PreTrainedTokenizerFast(tokenizer_object=tok, bos_token='<s>', eos_token='</s>',
                               unk_token='<unk>', pad_token='<pad>')
os.makedirs('/tmp/tiny', exist_ok=True)
fast.save_pretrained('/tmp/tiny')
cfg = GPT2Config(vocab_size=len(fast), n_positions=1024, n_embd=128, n_layer=4, n_head=4,
                 bos_token_id=fast.bos_token_id, eos_token_id=fast.eos_token_id,
                 pad_token_id=fast.pad_token_id)
GPT2LMHeadModel(cfg).save_pretrained('/tmp/tiny')
PY

# обучение тем же скриптом, что пойдёт в облако
/tmp/venv/bin/python tools/training/finetune.py --data tools/training/dataset \
  --out /tmp/tiny-out --steps 150 --model /tmp/tiny --revision main \
  --targets c_attn --eval-count 6
```

Ожидаемый результат: потеря на отложенной выборке падает (у нас 8.038 → 7.682
за 150 шагов, 31 секунда), в `/tmp/tiny-out/adapter` появляется
`adapter_model.safetensors`, а при загрузке видно 12 288 ненулевых весов LoRA.
Текст такая модель, разумеется, не порождает — она проверяет код, а не ум.
