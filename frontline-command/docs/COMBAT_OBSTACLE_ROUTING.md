# Obstacle detours while fighting

Previously `smart_route.js` explicitly excluded units with enemy contact. An infantryman who could see a target but had an obstacle in front of its movement goal could keep trying the same direction without asking for a route.

The existing short-range obstacle sensor and bounded EasyStar search may now run for fighting infantry with a currently observed, live target and without a hold-fire, hold-position, retreat or regroup order. The soldier can keep moving and shooting while a search runs. Since a search may finish after the soldier has moved, it is joined only via an independently collision-checked segment to an early waypoint; it is discarded if the unit moved over 160 px, the world/goal/target changes, the target moves more than 24 px or contact is lost. A combat route is rejected if sampled waypoints would leave the target outside vision or behind an opaque obstruction. The soldier may temporarily move away from its target and continue the same route outside weapon range, while contact remains valid. Movement collision, line-of-sight rules and firing checks remain in force. Non-combat searches keep the original 32 px start-drift limit. One planner job per game and a 64-operation slice per tick still apply. No user setting or experimental mode was added.

## Evidence and limits

- `tests/combat-obstacle-routing.mjs`: actual `Game.step`, real soldier AI and firing, but a **synthetic U-shaped movement obstacle**, mocked clear sight, a stationary durable opponent, extended vision, and other game systems disabled. In eight mirrored/repeated trials the pre-change version started no search and 0/8 got closer than the normal preferred range within 80 simulated seconds; the new version searched, safely moved around, fired, and reached that range in 8/8 (about 5.6 seconds). This is not eight independent combat maps. It also checks moving/hidden opponents, hold and retreat cancellation, and rejects a detour that would lose vision. Collision is sampled along each step; it is not a proof for every geometry.
- `tools/combat-obstacle-realmap.mjs`: actual terrain/walls, a fixed durable target and extended vision, isolated `Game.step` AI, one seed and selected positions. 80 real-map start/target pairs, tried in each direction with different factions: pre-change 132/160 reached preferred range, new 134/160, two improvements and no regressions by that criterion; neither version reached it in 26/160. Search occurred in 59/160 new cases and a combat route was observed in 9/160. No sampled wall/terrain crossing. Selection makes the near obstacle a condition only in the first direction; these are correlated placements on one map, not independent full wars.
- `tools/combat-obstacle-battles.mjs`: eight paired 120-second normal AI-vs-AI runs. New combat searches observed in 127 once-per-second samples and active routes in 7; baseline has neither. Total kills 383 before / 399 after; no wars ended. Same seeds do not keep RNG streams aligned after decisions diverge. This neither proves improved balance, wins or performance, nor establishes how many searches completed between samples.
- Chromium checked the real game config, the synthetic combat case for both factions, existing U routing, HQ wall orders and live ticks. Full `npm test` reached the final performance test with earlier checks passing, but failed at 500 units: 22.37 ms/tick vs the 22.22 ms limit. A separate sequential run passed on that machine (baseline 400/500: 15.67/22.16 ms, new 15.38/21.98 ms). These noisy numbers measure Node simulation only, not browser frame rate or performance equivalence.

This does **not** solve every obstruction: building-interior endpoints, vehicle combat, lost sight, moving targets, crowded paths, a single busy search slot, long distances and the conservative vision guard can still prevent or delay a detour. The real-map results include 26 unresolved cases. The separately running model training is unrelated and is not part of this change.
