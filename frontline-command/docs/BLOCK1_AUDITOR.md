# Проверяющий первого блока

`npm run audit:block1` — отдельный автоматический проверяющий, а не автономная
модель, которая самостоятельно пишет код или работает после окончания сессии.
Он запускает доступные тесты, фиксирует результаты и завершает процесс с кодом 1,
если хотя бы один обязательный пункт не пройден, отсутствует или не запускался.
`npm run audit:block1:quick` — короткая диагностика, она **никогда** не является
полной приёмкой. Полный прогон может занимать существенно больше времени,
особенно когда будет реализован 30-минутный soak.

На момент первого полного запуска (`BLOCK1_AUDIT_BASELINE.json`) обычный
`npm test` прошёл, U-ловушка с настройками игры по умолчанию дала 8/18,
приёмочные сценарии ниже отсутствовали. Позже добавлен стенд проходов и колонны: одиночные проходы успешны, колонна пока не проходит (`BLOCK1_DOORS.md`). Поэтому вердикт `NOT_ACCEPTED`.
Исторический JSON не является действующей приёмкой: запускать проверяющий надо
повторно на текущем состоянии проекта.

## Как проверяется

Проверяющий запускает именно конфигурацию по умолчанию для U-сцены: успех
экспериментального выключенного флага не маскирует проблему реальной игры.
Частичные unit-тесты не подменяют карточки ALG-04/18/19/21/22 или S1/S8/S9/S10.
Для будущих приёмочных сценариев он ожидает отдельные исполняемые файлы
`tests/acceptance/block1-*.mjs`, указанные в `requirements` проверяющего.
Каждый должен завершаться успешно и выводить один JSON-объект с `passed: true`
и доказательными полями, которые проверяет `validateEvidence`. Отсутствие файла,
неверный JSON, пустой результат, неудачный процесс и пропуск — не успех.
Тесты `tests/block1-auditor.mjs` проверяют эти правила.

Среди проверяемых границ: минимум 100 повторов для каждого обозначенного
прохода и колонны, отдельные сценарии застреваний, снижение диагностического
показателя как минимум на 70%, фактические локальные перестроения с бюджетом,
полнота сохранения и повтор, реальный браузерный `requestAnimationFrame` при
400/500 юнитах, реальный 30-минутный soak (контролируется и фактическое время
дочернего процесса). Обратная величина headless-тика не считается FPS браузера.

Проверяющий должен оставаться консервативным и проверяемым: сами результаты
будущих приёмочных программ также требуют осмысленных тестовых сцен и ревью;
формальный JSON или фиктивные измерения не заменяют испытание. Критерии блока 1
не означают готовность следующих блоков или всех S1–S10. Этот инструмент не
управляет разработкой и не запускается автоматически в фоне.

## Браузерный FPS

Добавлен реальный браузерный стенд `tests/acceptance/block1-browser-fps.mjs`.
Подробная методика, требования к среде и границы первого результата описаны в
`BLOCK1_BROWSER_FPS.md`, исходные данные — в `BLOCK1_BROWSER_FPS_BASELINE.json`.
Последний полный запуск: `browser_fps: fail`; программный headless-рендеринг
не доказывает производительность на пользовательской видеокарте. Стенд не
подменяет отдельные проверки скриншотов или 30-минутного soak.

## Коды и передача ошибок

Проверяющий выдаёт **устойчивые коды в диапазоне 0–999**. 000 зарезервирован
для отсутствия ошибок и никогда не записывается в список ошибок; свободные
номера не заполнены выдуманными неисправностями. Коды отражают конкретные
факты, а не их предполагаемую причину. Несколько ошибок одной проверки могут
иметь разные коды; один код может повторяться в разных сценах.

* `npm run audit:block1:human` — полный человекочитаемый отчёт: код, факт,
  требование и рекомендуемая проверка.
* `npm run audit:block1:quick:human` — быстрая диагностика: пропущенные
  проверки отмечены кодом 003, приёмка в этом режиме невозможна.
* `npm run audit:block1` — полный JSON (версия 2, существующие `checks` и
  `verdict` сохранены, добавлен `issues[]`). В каждом элементе есть числовой
  `code`, идентификатор проверки, статус, сообщение, факт, требование и действие.
  Подробные результаты остаются в `checks[].evidence`; пояснения не заменяют
  доказательства и не ослабляют валидатор.

Ненулевой код **процесса** означает, что приёмка не пройдена; он не является
кодом неисправности. Если процесс или сценарий сломан, если данные повреждены
или проверка отсутствует, это отдельная блокирующая ошибка, а не успех.
Программа сообщает факты и возможные действия, но не исправляет их сама и не
работает автономно в фоне. Браузерный результат в программной headless-среде
нельзя выдавать за результат на пользовательском GPU.

### Встречные проходы
