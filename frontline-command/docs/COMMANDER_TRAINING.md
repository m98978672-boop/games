# Пробное обучение Qwen для Frontline

Это исследовательское дообучение **помощника**, не полноценного командира. Оно не устанавливает результат в игру и не доказывает улучшение стратегии.

## Данные

`node tools/training/collect-commander.mjs OUTPUT_DIRECTORY` собирает реальные `commanderSnapshot` в боях штатного ИИ на 4 обучающих и 2 проверочных seed, по 120 игровых секунд с перестановкой сторон. Метки формирует простая эвристика, а не человек или обученная модель: сначала снабжение при боезапасе меньше 70%, иначе строительство с инженером при наличии чертежа, иначе удержание первой своей точки или ничего. Эта эвристика не оценивает полезность приказа и может навредить. Это имитация правил, не обучение на победах и не сбор экспертных демонстраций.

Сторона видит только свою сводку, без фракции, координат, вражеских данных, истории и времени. В метаданных сохранены seed и перестановка для аудита, но в prompt они не передаются. Проверочные seed отделены от обучающих, одинаковые входы удаляются из обоих наборов; файлы и их SHA-256 хранятся в `manifest.json`. В начальном прогоне получилось 104 обучающих и 52 проверочных разных примера. Нет гарантии отсутствия семантически похожих состояний, данные малы и несбалансированы, сценарии с `none` в этой выборке могут отсутствовать.

Сборщик по умолчанию использует базовую инструкцию обычного эксперимента. Флаг `--knowledge` выбирает инструкцию режима «помощник со знаниями»; и сборщик, и worker импортируют её из одного `src/ai/commander-prompts.js`. Метки и сводки при этом не меняются. Прежние результаты ниже относятся к базовой инструкции и не доказывают качества нового режима. Ни один исследовательский адаптер не подключён к игре.

`node tests/commander-training-data.mjs` проверяет изоляцию, воспроизводимость, разделение и метки через игровой валидатор. Это не проверка модели.

## Метод

`tools/training/train-qwen.py` с закреплёнными версиями из `.github/workflows/frontline-qwen-training.yml` проверяет SHA-256 исходных полных весов `Qwen/Qwen3.5-0.8B` ревизии `2fc06364715b967f1860aea9cf38778875588b17`, а не WebLLM ZIP. Используется LoRA (rank 8) для q_proj/v_proj, исходные веса заморожены. Система и формат входа берутся из worker игры; токены prompt и ответа кодируются раздельно, как при генерации. Лосс считается только на токенах размеченного ответа. Никаких дополнительных сведений о противнике в обучение не подаётся.

Пример запуска (нужны Python, PyTorch, Transformers, PEFT, доступ к Hugging Face, достаточно памяти и времени):

```sh
node frontline-command/tools/training/collect-commander.mjs /path/to/data --knowledge
python frontline-command/tools/training/train-qwen.py --data /path/to/data --output /path/to/output --steps 32 --eval-count 8
python frontline-command/tools/training/eval-qwen.py --data /path/to/data --adapter /path/to/output/adapter --output /path/to/generated.json --count 8
node frontline-command/tools/training/score-generated.mjs /path/to/generated.json
```

Отчёт сравнивает **teacher-forced loss** на нескольких отложенных примерах до и после. Текущий сценарий выбирает разные действия и seed, когда они доступны; даже восемь примеров — очень узкая проверка. Перед обучением все собранные train/eval примеры проверяются токенизатором Transformers: префикс плюс резерв 96 выходных токенов должны уложиться в 1024. Это не измерение шаблона WebLLM и не гарантия для любых будущих сводок. Это лишь мера соответствия искусственным меткам, а не качество самостоятельного JSON, поведение в бою, баланс сторон или выигрыш. Слишком короткий прогон может не улучшить даже эту метрику. Результат — PEFT-адаптер для полной модели, не автономная модель, не MLC и не совместим с ZIP-импортом в браузере.

## Результат короткой проверки

[Пробный адаптер и данные](https://github.com/m98978672-boop/games/releases/tag/frontline-qwen35-lora-research-44361283962): 1 шаг оптимизатора, 319 488 обучаемых параметров LoRA. Лосс на одном отложенном примере `hold`: 0,11863 → 0,08538. Это не проверка общей способности.

Более длинный восьмишаговый прогон завершил вычисления: на четырёх первых примерах проверки (все `hold`, seed 201) лосс составил 0,12265 → 0,07186. Однако публикация адаптера завершилась HTTP 403, и файлы этого прогона не были сохранены: использовать их нельзя. Следующий прогон сохраняет артефакты до публикации и публикует их отдельным заданием; успех публикации не гарантирован.

[Отчёт свободной генерации](https://github.com/m98978672-boop/games/releases/tag/frontline-qwen35-eval-44364153124): три отложенные ситуации, исходная модель выдала 0/3 допустимых приказов, с одношаговым адаптером — 1/3. Проверка выполнена на CPU через Transformers **без** JSON-грамматики WebLLM, а не в браузере и не в бою.

[Повторный восьмишаговый адаптер](https://github.com/m98978672-boop/games/releases/tag/frontline-qwen35-lora-research-44366582436) сохранён. Teacher-forced loss на четырёх отложенных примерах трёх типов уменьшился с 0,21555 до 0,19180. В [трёх независимых от обучения тестовых ситуациях](https://github.com/m98978672-boop/games/releases/tag/frontline-qwen35-eval-44368033484) исходная модель выдала 0/3 допустимых предложений, адаптер — 3/3, но все три были одинаковым приказом `hold`, и только один совпал с эвристической меткой. Эти три примера не доказывают улучшение игры. Адаптер в игру не внедрён.

## Прогон с инструкцией знаний, 32 шага

[Адаптер и данные](https://github.com/m98978672-boop/games/releases/tag/frontline-qwen35-lora-research-44375607542), [ответы и оценка](https://github.com/m98978672-boop/games/releases/tag/frontline-qwen35-eval-44375607542). Выполнено 32 шага LoRA, 319 488 обучаемых параметров, без изменения базовых весов. На 8 примерах из отложенных seed средний teacher-forced loss уменьшился с 0,28519 до 0,17737. Это только соответствие эвристическим меткам.

Свободная CPU-генерация на этих же 8 примерах (не использовались для градиентов, но использовались для проверки лосса) без JSON-грамматики WebLLM: базовая модель 0/8 допустимых, адаптер 5/8; точное совпадение с эвристикой 0/8 и 4/8 соответственно. Семь примеров взяты из seed 201, один — 202, без перестановки сторон и без `none`; они могут быть похожи между собой. Все ответы адаптера выбрали отряд с индексом 0, в том числе когда нужен другой: 3 ответа не прошли валидатор. Эти наблюдения выявляют серьёзную ошибку, а не доказывают стратегическое улучшение. Две программы используют разные форматы и режимы генерации, поэтому результат нельзя переносить на WebLLM.

В собранной выборке максимальный префикс через Transformers-токенизатор составил 651 токен, с резервом 96 — 747 из 1024. Это не гарантия для других состояний или шаблона WebLLM. Адаптер — PEFT, в игре не используется; необходимо объединение и MLC-конвертация, а также реальная браузерная и игровая проверка.

## Что необходимо до использования в игре

Нужны более содержательные проверенные данные и разнообразные состояния; измерение реальных сгенерированных команд и парных боёв на отложенных seed (обе стороны, меняя местами); проверка отказов, задержек и FPS; объединение адаптера с совместимой базой и конвертация/квантование в MLC; контроль корректности артефактов; полноценный инференс WebGPU на устройстве с shader-f16. Лишь после подтверждения результатов можно решать вопрос интеграции. В обычной игре нейросеть не используется; доступные раньше пункты для неё скрыты из пользовательского меню, исследовательский код сохранён.
