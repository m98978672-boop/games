# PLAYBRIDGE — что уже реально работает и как продолжать

PLAYBRIDGE собирает в одном интерфейсе два сценария, но они не симметричны:

1. **Установка на свой компьютер:** приложение получает настоящий список игр через Steam Web API и передаёт установку официальному клиенту Steam по `steam://install/<AppID>`. Если Steam считает подходящим источник в той же локальной сети, передачу выполняет сам Steam; иначе используется его CDN. PLAYBRIDGE не копирует и не раздаёт игровые депо.
2. **Облачная игра:** для неё нужны GPU-хосты, потоковое видео, поддержка конкретных игр и отдельное разрешение/партнёрская схема. Пока провайдера нет, кнопка запуска намеренно выключена: фиктивных регионов, задержек и «подключённых» сессий больше нет.

## Реализованное ядро

- Backend на Node.js без сторонних зависимостей (`server.mjs`): Steam OpenID flow, проверка ответа обратно через endpoint Steam, короткоживущая подписанная HttpOnly-cookie-сессия.
- `GET /api/session`, `GET /api/status`, `GET /api/games` и `POST /api/logout`.
- Список библиотеки берётся только у Steam Web API и только для вошедшего SteamID. Для него нужен серверный `STEAM_WEB_API_KEY` и публичные настройки «Сведения об играх» в профиле Steam.
- Карточка игры показывает настоящий AppID и время запуска; «Установить в Steam» передаёт AppID официальному Steam-клиенту, а «Страница Steam» ведёт в официальный магазин.
- При отсутствии backend/API key UI показывает конкретное состояние и инструкцию; вымышленные игры не подставляются.
- Облачный запуск явно помечен недоступным, пока нет реального provider adapter и согласованной инфраструктуры.
- Набор тестов без реального входа в Steam: подписи сессий, валидация SteamID/OpenID, проверка redirect URI, состояния API.

## Запуск локально

Нужен Node.js 22 или новее. В каталоге `cloud-play`:

```bash
cp .env.example .env
```

Открой `.env` и задай:

- `PUBLIC_ORIGIN=http://localhost:4174` для локального теста;
- `SESSION_SECRET` — случайная строка не короче 32 символов (например, `openssl rand -hex 32`);
- `STEAM_WEB_API_KEY` — ключ Steam Web API. Создаётся в настройках Steam Community Web API; он нужен только backend и **не должен попадать в JavaScript, HTML, Git или чат**.

Затем:

```bash
npm test
npm run dev
```

Открой `http://localhost:4174/cloud-play/`, нажми «Войти через Steam» и подтверди вход на домене Steam. Steam перенаправит обратно на локальный callback. Если список пустой, открой настройки приватности профиля Steam и разреши показ «Сведений об играх».

На сайте GitHub Pages backend не запускается: там будет честный статус «API offline». Для публичного входа нужен отдельный Node-хост с HTTPS-доменом.

### Самостоятельный VPS через Docker и Caddy

В `cloud-play/.env` задай:

```env
PLAYBRIDGE_DOMAIN=playbridge.example
PUBLIC_ORIGIN=https://playbridge.example
SESSION_SECRET=<случайная строка из openssl rand -hex 32>
STEAM_WEB_API_KEY=<ключ Steam Web API>
```

Укажи DNS A/AAAA-запись домена на VPS, открой входящие порты `80` и `443`, затем выполни из `cloud-play/`:

```bash
docker compose up -d --build
```

Caddy автоматически получит HTTPS-сертификат и проксирует сайт, `/api/*` и `/auth/*` на Node. Для другого хостинга нужен тот же принцип: HTTPS reverse proxy, один origin для фронтенда и API, секреты из secret manager. Не включай CORS для всех доменов и не запускай публичный OpenID callback через HTTP.

## Как довести установку до полезного MVP

1. Оставить Steam источником владения и контента; не использовать аккаунт пользователя для обхода лицензирования.
2. Использовать встроенный Steam Local Network Game Transfer для устройств в одной сети. Страница только открывает `steam://install/<AppID>`; Steam сам выбирает источник с учётом своих настроек.
3. Для удалённых пользователей пока направлять в официальный Steam CDN. Независимая раздача кэша игровых файлов — только после официального соглашения с Valve и правообладателями.
4. Позже можно добавить desktop-компаньон, который проверяет, что Steam установлен, и помогает включить LAN transfer. Он не должен расшифровывать депо или подменять Steam-клиент.

## Облачный запуск — конкретный план

Нельзя включить его одной кнопкой в статическом сайте. Нужны последовательно:

1. **Право и провайдер.** Подтвердить условия cloud gaming с Valve/издателями и выбрать партнёра с GPU API. Если своего GPU-пула нет, сначала интегрировать провайдера, который уже умеет запускать Steam-игры по пользовательской лицензии.
2. **Список совместимости.** Начать с 1–3 согласованных игр; проверить DRM, античит, пользовательский вход и правила многопользовательского режима. Не обещать запуск всего каталога.
3. **Оркестратор сессий.** Backend проверяет доступ к игре, резервирует изолированную виртуальную машину, запускает официальный Steam-клиент, применяет лимиты по времени и закрывает VM после выхода.
4. **Поток.** WebRTC для видео/аудио и обратного канала управления, STUN/TURN для NAT, аппаратное кодирование на GPU. Секреты и Steam-сессия не попадают в браузерную базу данных; вход пользователя проходит только поддерживаемым Steam/провайдером способом.
5. **Состояние и очистка.** Сохранять прогресс через Steam Cloud только для поддерживаемых игр, затем гарантированно очищать эфемерный диск и завершать аренду GPU.
6. **Экономика.** Ограничить регионами и тарифами; измерять задержку и стоимость GPU/трафика. Только после этого включать кнопку и показывать реальные доступные регионы.

Пока ни партнёрский API, ни облачный GPU-пул не выбраны, безопасное состояние — `cloud.ready = false`. Следующий код облачного режима должен быть конкретным адаптером выбранного провайдера, а не симуляцией потока.

## Границы и безопасность

- Steam OpenID подтверждает SteamID, но не раскрывает файлы игр и не открывает приватную библиотеку.
- API key хранится только на сервере; пароли Steam приложение не запрашивает и не сохраняет.
- Список игр может быть пустым, если профиль или «Сведения об играх» закрыты. Настройки приватности не обходятся.
- Обычная GitHub Pages — статический хостинг; реальный callback и приватные API-ключи требуют отдельного backend.
- PLAYBRIDGE — независимый проект, не связанный с Valve или Steam. Перед публичным или коммерческим запуском нужна проверка договоров и условий использования.
