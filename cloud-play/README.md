# PLAYBRIDGE — реальное состояние и план

PLAYBRIDGE объединяет два отдельных сценария:

1. **Установка на свой компьютер:** библиотека запрашивается у Steam Web API после входа через Steam OpenID. Ссылка установки открывает официальный Steam-клиент (`steam://install/<AppID>`); локальную передачу или CDN выбирает сам Steam. PLAYBRIDGE не копирует игровые депо.
2. **Удалённая/облачная игра:** допустимый GPU-хост может быть компьютером самого пользователя или арендованной машиной. Сейчас ни host-agent, ни сопряжение устройств, ни видеопоток не подключены, поэтому запуск отключён и никаких фиктивных сессий не показывается.

## Реализовано

- Backend на Node.js без сторонних зависимостей: Steam OpenID, проверка assertion напрямую через Steam и короткоживущая подписанная HttpOnly-cookie-сессия.
- `GET /api/session`, `GET /api/status`, `GET /api/games` и `POST /api/logout`.
- Библиотека берётся только у Steam Web API и только для вошедшего SteamID. Нужны серверный `STEAM_WEB_API_KEY` и доступные настройки приватности «Сведения об играх».
- Установки передаются официальному Steam-клиенту. PLAYBRIDGE не раздаёт депо; LAN transfer управляется самим Steam.
- Устанавливаемая PWA: manifest, иконки, кнопка установки в поддерживаемых браузерах и service worker для автоматической проверки/применения интерфейсных обновлений.
- Service worker кэширует только статическую оболочку. `/api/*`, `/auth/*`, Steam-сессии и библиотека пользователя не кэшируются.
- Облачный/удалённый запуск остаётся выключенным до реальной реализации host-agent, безопасного сопряжения и совместимого потокового клиента.
- Тесты проверяют OpenID, серверную библиотеку и раздачу PWA-ресурсов.

## Локальный запуск и Steam

Нужен Node.js 22 или новее. Из каталога `cloud-play`:

```bash
cp .env.example .env
```

Заполни `.env`:

- `PUBLIC_ORIGIN=http://localhost:4174` для локального теста;
- `SESSION_SECRET` — случайная строка длиной не менее 32 символов, например `openssl rand -hex 32`;
- `STEAM_WEB_API_KEY` — ключ Steam Web API. Он хранится только на backend и не должен попадать в JavaScript, HTML, Git или чат.

Затем:

```bash
npm test
npm run dev
```

Открой `http://localhost:4174/cloud-play/`. Вход перенаправит пользователя на официальный Steam OpenID; пароль Steam приложение не собирает. Если игры не отображаются, проверь публичность «Сведений об играх» в Steam.

GitHub Pages отдаёт статические файлы и не запускает Steam backend. Для реального входа нужен backend за HTTPS reverse proxy. Фронтенд и API должны быть доступны с согласованной конфигурацией origin; отдельный backend не превращает GitHub Pages в сервер.

## Установка приложения и автообновления (PWA)

- На HTTPS-сайте браузер предложит установить PLAYBRIDGE; в Chrome/Edge кнопка «Установить» появится внутри страницы, когда браузер сочтёт приложение готовым к установке. На iOS Safari используй системное меню **Поделиться → На экран “Домой”**.
- Для разработки service worker работает на `localhost`; на других адресах нужен HTTPS.
- При открытии приложения, возвращении вкладки в фокус и затем раз в час PLAYBRIDGE вызывает `registration.update()`. Новый service worker предварительно загружает статическую оболочку, активируется без ручного подтверждения и перезагружает страницу, чтобы применить обновление; поиск, фильтр, число показанных игр и позиция страницы восстанавливаются.
- Перед выпуском новой версии синхронно обновляй `version` в `package.json` и `manifest.webmanifest`, а также суффикс `CACHE_NAME` в `sw.js`; затем публикуй все файлы из `cloud-play/`. Service worker запрашивается без HTTP-кэширования, а ресурсы новой оболочки принудительно перечитываются.
- В офлайне может открыться закэшированная оболочка, но Steam-вход, библиотека и backend-функции требуют сети. PWA — это устанавливаемое веб-приложение, не Windows `.exe` и не нативный macOS/Linux-клиент.

## Самостоятельный VPS через Docker и Caddy

В `cloud-play/.env` задай:

```env
PLAYBRIDGE_DOMAIN=playbridge.example
PUBLIC_ORIGIN=https://playbridge.example
SESSION_SECRET=<случайная строка из openssl rand -hex 32>
STEAM_WEB_API_KEY=<ключ Steam Web API>
```

Направь DNS A/AAAA-запись на VPS и открой входящие порты `80` и `443`. Из каталога `cloud-play/` запусти:

```bash
docker compose up -d --build
```

Caddy получает HTTPS-сертификат и проксирует сайт, `/api/*` и `/auth/*` на Node. На другом хостинге нужен тот же принцип: HTTPS reverse proxy и секреты из secret manager. Не включай CORS для всех доменов и не запускай публичный Steam OpenID callback через HTTP.

## Собственный GPU-компьютер как хост

Коммерческий GPU-провайдер не является обязательным. Для личного использования можно рассматривать постоянно включённый компьютер пользователя с GPU и установленным официальным Steam-клиентом. Это пока только план интеграции: PLAYBRIDGE не умеет обнаруживать такой компьютер, будить его, запускать игру или передавать видео.

Варианты для прототипа:

1. **Steam Remote Play / Steam Link** — наиболее прямой путь для личного компьютера и собственных устройств: игру и поток обслуживает Steam. В текущем PLAYBRIDGE нет сопряжения с Steam Remote Play и нет встроенного клиента потока; открыть библиотеку в веб-приложении недостаточно, чтобы запустить удалённую сессию.
2. **Sunshine на хосте + Moonlight-клиент** — самостоятельный вариант хоста/клиента. Это не готовая интеграция в текущую веб-страницу: для браузерного сценария потребуется совместимый клиент или реальный шлюз видеопотока, сигнализация, передача управления и диагностика сети.
3. **Свой host-agent** — отдельный процесс на GPU-компьютере, который после явного сопряжения принимает ограниченные команды PLAYBRIDGE. Его ещё нужно спроектировать и реализовать; текущий backend таких команд не принимает.

Минимальные требования безопасности до включения любой сессии:

- одноразовое сопряжение с коротким сроком действия; отдельный секрет/ключ каждого хоста хранить в системном хранилище, а не в браузере;
- не передавать и не сохранять пароль Steam, cookies Steam или Steam Web API key на host-agent;
- разрешать запуск только AppID, выбранных вошедшим пользователем, и только локальным официальным Steam-клиентом; не обходить DRM/античит и не раздавать депо;
- не выставлять удалённый рабочий стол или административный порт хоста в публичный интернет; продумать исходящее защищённое соединение, VPN либо корректный relay для NAT;
- ограничивать длительность/число сессий, подтверждать остановку процесса и показывать реальные статусы; если используется WebRTC, отдельно настроить защищённую сигнализацию и TURN для сложных NAT-сетей.

Потенциальный путь для личного GPU — сначала проверить Steam Remote Play между своими устройствами, затем решить, нужен ли веб-клиент или отдельный десктопный клиент. Это не означает, что PLAYBRIDGE уже умеет стримить. До реализации и тестирования этих частей API оставляет `cloud.ready = false`, а кнопка запуска выключена.

## План развития установки

1. Сохранять Steam источником владения и контента; не использовать аккаунт пользователя для обхода лицензирования.
2. Для устройств в одной сети использовать встроенный Steam Local Network Game Transfer. PLAYBRIDGE передаёт только AppID официальному клиенту.
3. Для удалённой установки использовать официальный Steam CDN. Независимая раздача игровых файлов возможна только при необходимых разрешениях Valve и правообладателей.
4. Позже можно сделать desktop-компаньон, который проверяет наличие Steam и помогает включить LAN transfer, не расшифровывая депо и не подменяя Steam.

## Границы и безопасность

- Steam OpenID подтверждает SteamID; приватную библиотеку и сведения, скрытые настройками профиля, нельзя обходить.
- Steam Web API key хранится только на сервере; пароль Steam приложение не запрашивает и не сохраняет.
- GitHub Pages — статический хостинг; для Steam-входа нужен отдельно запущенный backend.
- Установленная PWA автоматически обновляет только интерфейсные файлы; это не автообновление Steam-игр и не установка новых игровых депо.
- PLAYBRIDGE — независимый проект, не связанный с Valve или Steam. Перед публичным/коммерческим запуском проверь условия платформы и права на конкретные игры.
