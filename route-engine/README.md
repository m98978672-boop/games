# Движок маршрутов — первый изолированный прототип

## Статус

Работает независимый детерминированный поиск кратчайшего пути по направленному графу с неотрицательными весами. Узлы и рёбра задаёт вызывающая игра: это **не генератор карты и не физический движок**. На графе поддерживаются переходы типа «дверь» и «ворота»: учитываются ширина, радиус, состояние, возможность открытия, тип юнита и цена открывания. Результат содержит предложенные действия, но не открывает двери и не двигает юнитов.

RatCore найден в PR [#250](https://github.com/m98978672-boop/games/pull/250), снимок `139e2a6b018af3c69b33d6b2c3deb748305b1d97`: там есть спецификация, но **исполняемого RatCore пока нет**. Поэтому связать и проверить два работающих движка сейчас невозможно. Этот прототип **не реализует** `RatCore.tools.nav.*`, `ToolGuard`, `BridgeGuard` или протокол RatCore и не объявляет себя совместимым по безопасности. Границы будущего подключения описаны в `RATCORE_INTEGRATION.md`.

Отдельный адаптер `adapters/frontline-door.mjs` считывает параметры реально существующего дверного проёма Frontline. Он не строит остальной граф и не подключён к игровому циклу. Ни настройки Frontline, ни работа ботов, ни опубликованная игра этим прототипом не меняются.

## API

ES modules, без зависимостей, браузер или Node.js:

```js
import { createSnapshot, beginSearch } from './src/router.mjs';

const revision = 'world-42';
const graph = createSnapshot({
  revision,
  nodes: ['inside', 'outside'],
  edges: [{
    id: 'door-out', from: 'inside', to: 'outside', cost: 5,
    portal: {
      id: 'hq:door-0', kind: 'door', state: 'closed',
      width: 40, openable: true, openCost: 3
    }
  }]
});
const job = beginSearch(graph, {
  from: 'inside', to: 'outside', radius: 8, vehicle: false,
  hostRevision: () => revision
});
let r;
do { r = job.step(64); } while (r.status === 'running');
// found: nodes, edges, actions [{ edgeId, portalId, kind, action }], cost
// action: 'open-and-cross' либо 'cross'
```

- Каждое ребро направленное: обратное добавляется отдельно. `cost` и `openCost` — неотрицательные конечные числа в общих единицах стоимости. `width` и `radius` — в одних единицах; требуется `width > 2 × radius`. Для физического запаса вызывающий должен его явно учесть.
- Для `vehicle: true` дверь непроходима, ворота возможны. `blocked` и закрытая неоткрываемая дверь исключаются. Для открываемой закрытой двери к цене ребра прибавляется `openCost`. Доступность прав и конкретных типов транспорта пока задаёт вызывающий; окна не поддерживаются как проход.
- `createSnapshot` проверяет и копирует входные данные (до 100 000 узлов и 500 000 рёбер); в нём нет ссылок на изменяемые объекты дверей. Порядок одинакового входа и стоимости детерминирован. Подделанный объект, имитирующий snapshot, API не рассматривается как граница безопасности.
- На каждом `step` проверяется `hostRevision()`. При изменении возвращается `stale`, при исчерпании графа — `unreachable`, отмена `cancel()` возвращает `cancelled`. Хост обязан менять версию **до** изменения геометрии, состояния или доступа, в том числе при отложенном пересчёте. Нельзя строить снимок на неопределённой/ожидающей перестройки версии. После нахождения пути хост должен дополнительно проверять версию и актуальную физическую проходимость при исполнении каждого перехода.
- Бюджет `step(1..10000)` измеряется количеством извлечений из очереди и обработанных рёбер. Построение снимка и сборка результата выполняются синхронно и этим бюджетом **не ограничены**; поиск не гарантирует фиксированное время кадра. При очень высокой связности и больших графах необходимы профилирование, ограничения и/или worker.

## Математика

Для пути `P` стоимость `C(P) = Σ cost(e) + Σ openCost(e)` по закрытым открываемым дверям. Поиск поддерживает `g(v)` — наименьшую найденную цену от старта; извлекает узел с минимальным `g`, обновляет `g(v) ← min(g(v), g(u) + c(u,v))`. При неотрицательных весах это Дейкстра, частный случай A* с `h=0`. Он находит минимальную стоимость **в предоставленном графе**, но не обязательно в настоящем мире: если игра неверно описала стены, ширину, доступность или цену, результат не становится физически правильным. Не используется сглаживание, которое могло бы срезать стену.

## Что проверено

```sh
npm --prefix route-engine test
# При установленном npm ci в frontline-command:
npm --prefix route-engine run test:browser
```

- Тесты на синтетических графах: открывание, закрытые и заблокированные двери, ворота, размеры и недоступные цели; отмена, устаревание, копирование снимка, валидация, равенство ширины и диаметра, ограниченный пошаговый поиск.
- 100 воспроизводимых случайных направленных графов, 1200 запросов: стоимость результата сравнена с независимым Floyd–Warshall. Это не нагрузочная проверка игры и не доказательство для всех входов.
- В Chromium проверены загрузка ES-модуля и поиск пути с закрытой дверью. Это дымовой тест модуля, не браузерная игра и не замер FPS.
- `tests/frontline-adapter.mjs` создаёт реальные игровые объекты штабов **обеих фракций**, закрывает дверь, считывает её параметры и строит граф из одного искусственного перехода. Проверяется предложенное действие открытия без изменения двери и отмена поиска при ожидающем пересчёте. Тест не доказывает, что подступы физически доступны, и не двигает юнитов.

## Ещё не сделано

1. Генерация маршрута из реальной карты и проверка каждого перехода с учётом рельефа и геометрии, в том числе подступов к дверям и транспортных габаритов.
2. Исполнитель действий открытия, ожидания и прохода; перепроверка перед движением, закрытие двери на юните, смерть и изменение цели.
3. Очередь, резервы пространства-времени, столкновения, разъезд и предотвращение голодания. **Этот прототип не мешает двум ботам пересечься**, не реализует требование о совместном движении и не доказывает отсутствие тупиков.
4. Адаптер к реальному RatCore, когда появятся реализация и утверждённый интерфейс, затем интеграция во Frontline за флагом с тестами полного `Game.step`, обеих сторон, боя, логистики и браузерной производительности.
