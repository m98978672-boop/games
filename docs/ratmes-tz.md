> Статус документа: **черновик спецификации v1.0** (этап проектирования и изучения материалов; код приложения ещё не пишется).
> Дата: 2026-11-16.

## 1. Идея и главная цель продукта

**RatMes** — сверхбыстрый, всегда рабочий кросс-мессенджер с собственной перепиской и мостами ко всем популярным мессенджерам мира.

Ключевые принципы RatMes:
1. **Мгновенный отклик и постоянная работоспособность** — интерфейс никогда не «висит на крутилке» в ожидании сети; всё, что нужно пользователю прямо сейчас, читается локально за миллисекунды.
2. **Обычные файлы всегда в запасе** — все переписки, контакты и вложения (фото, видео, голосовые, документы) постоянно дублируются на диск в **обычных открытых папках и файлах**, которые можно открыть Блокнотом, просмотрщиком фото или файловым менеджером даже вообще без RatMes.
3. **Движок времени («Прошлое + Будущее + Сон»)** — умный планировщик, который помнит опыт прошлых сессий и сбоев, заранее готовит будущие действия и каналы связи, а в тишине сам наводит порядок, освобождает память и уходит в сон, чтобы в момент пиковой нагрузки не тормозить и не «уснуть».
4. **Единое окно во все популярные мессенджеры с учётом страны** — можно написать человеку в другой мессенджер прямо из RatMes, если выполнены реальные условия подключения (есть аккаунт, есть нужный VPN/прокси для заблокированных сервисов, запущен ПК-помощник там, где это требуется). Профиль страны по умолчанию — **Россия**, с возможностью выбрать **любую страну мира**.

## 2. Целевая платформа и архитектура запуска

Выбранная схема: **Браузер / PWA + локальный ПК-помощник (`RatMes Agent`)**.

### 2.1. Два компонента системы

1. **Клиент RatMes (Веб / PWA):**
   - Открывается в любом современном браузере на ПК и телефоне, устанавливается как PWA.
   - Хранит быстрый локальный кэш (IndexedDB / OPFS) и очередь исходящих сообщений.
   - Работает мгновенно даже при полном отсутствии интернета (чтение истории, поиск, черновики, постановка сообщений в очередь).

2. **Локальный ПК-помощник (`RatMes Agent`):**
   - Лёгкий фоновый сервис на компьютере пользователя (общается с клиентом по защищённому локальному каналу).
   - Отвечает за то, что браузер технически не может делать напрямую:
     - запись и синхронизация **обычных файлов в запасе** на реальный диск (`RatMes-Vault/`);
     - работа **мостов** в чужие мессенджеры (MTProto для Telegram, Multi-Device для WhatsApp, протоколы VK, MAX, Discord, Signal, Viber, LINE, KakaoTalk, WeChat, Zalo, Meta Messenger / Instagram DM и др.);
     - маршрутизация трафика конкретного моста через системный или выделенный **VPN / SOCKS5 / HTTP-прокси** (точечно: например, VK и MAX идут напрямую, а Telegram / WhatsApp / Discord — через прокси/VPN);
     - запуск собственных чатов **RatMes ↔ RatMes** (локальная сеть LAN/Wi-Fi + ретранслятор/P2P через интернет).

### 2.2. Два режима переписки

- **Свои чаты RatMes ↔ RatMes:**
  - Собственные аккаунты и ключи пользователей RatMes.
  - Работают через собственный лёгкий сервер-ретранслятор и/или прямое соединение в локальной сети (Wi-Fi/LAN) без привязки к сторонним корпорациям.
- **Кросс-мессенджерные чаты (Мосты):**
  - Внешний контакт виден в общем списке чатов (с понятным значком сети: `TG`, `VK`, `WA`, `DC`, `MAX` и т.д.).
  - Отправка и получение сообщений идут через адаптер моста на ПК-помощнике.

## 3. Хранилище: «Обычные файлы всегда в запасе»

Приоритет пользователя: **в запасе хранятся обычные файлы переписок и вложений**, пригодные к чтению без самого RatMes.

### 3.1. Двухслойное хранение

1. **Быстрый рабочий слой (для скорости UI):**
   - Локальный индекс (SQLite в режиме WAL на ПК-помощнике + IndexedDB в браузере) для мгновенного поиска, фильтрации и переключения чатов за <16 мс.
   - Этот слой считается *производным*: если он повредится или очистится, он полностью пересобирается из папки с обычными файлами.

2. **Главный файловый запас (`RatMes-Vault/` — источник правды):**
   - Простая, прозрачная структура папок на диске:
     ```text
     RatMes-Vault/
       README.txt                         # краткая памятка, как читать архив без RatMes
       contacts/
         contacts.json                    # список контактов и привязок к мессенджерам
       chats/
         ratmes/
           alex_id42/
             meta.json                    # название, участники, заметки
             2026-11.jsonl                # машиночитаемый append-only журнал (1 строка = 1 событие)
             2026-11.txt                  # человекочитаемый диалог (открывается Блокнотом)
             media/
               2026-11-16_14-20_photo.jpg # оригинальные файлы вложений с понятными именами
         telegram/
           ivan_tg/
             ...
         vk/
           maria_vk/
             ...
       outbox/
         pending.jsonl                    # очередь сообщений, ждущих сеть / VPN / ПК-агент
       engine/
         memory.json                      # сжатая «память прошлого» (привычки, журнал сбоев)
     ```

### 3.2. Гарантия сохранности файлов (Crash-Safety)

Чтобы при выключении электричества, падении процесса или зависании ПК ни один файл не превратился в битый «обрубок»:
- **Для заменяемых файлов** (`meta.json`, `contacts.json`, `memory.json`) используется строгий 6-шаговый протокол атомарной записи:
  1. Запись во временный файл `*.tmp` в той же папке.
  2. `fsync(tmp_fd)` — сброс данных на физический диск.
  3. Закрытие `tmp_fd`.
  4. Атомарный `rename(tmp, target)` (или `MoveFileEx` с `MOVEFILE_REPLACE_EXISTING` на Windows).
  5. `fsync(parent_dir_fd)` — фиксация записи каталога на диске.
  6. Только после этого операция считается завершённой.
- **Для журналов переписки** (`*.jsonl`, `*.txt`) используется **append-only запись по границам строк** (`\n` как маркер коммита): при старте после аварийного падения незавершённый «хвост» после последнего переноса строки аккуратно отсекается, и журнал остаётся валидным.
- **Для медиафайлов** — сначала дозапись во временный файл, проверка хэша, затем перенос в `media/`; дубликаты крупных файлов могут ссылаться на общий локальный кэш или сохраняться под чистым именем.
- **Transactional Outbox (надёжная очередь отправки):** исходящее сообщение сначала фиксируется в `outbox/pending.jsonl` со статусом (`queued -> sending -> sent | failed_condition`), а потом отправляется через мост. Даже при обрыве интернета или падении VPN сообщение не теряется.

## 4. Движок времени: «Прошлое + Будущее + Сон»

Главная архитектурная особенность ядра RatMes — **трёхфазный адаптивный планировщик**, который управляет памятью, сетью, кэшем и мостами.

### 4.1. Фаза «Прошлое» (Память и профиль эксплуатации)

Движок накапливает компактную локальную статистику (никакой внешней телеметрии — всё хранится только у пользователя):
- **Матрица переходов (мини-модель Маркова):** какие чаты и в какое время суток пользователь обычно открывает сразу после запуска или после конкретного диалога (`чат A -> чат B`).
- **Журнал стабильности каналов и мостов:** когда, на какой сети и по какой причине падал каждый мост (DNS-блок, таймаут, отвалившийся VPN, лимит `429 Retry-After`, потеря сессии).
- **Профиль стоимости операций:** сколько реально времени и ОЗУ занимали открытие конкретного тяжёлого чата, индексация и бэкап.

### 4.2. Фаза «Будущее» (Упреждающая подготовка)

На основе «Прошлого» и текущего состояния устройства движок заранее делает полезную работу в свободные миллисекунды:
- **Предзагрузка вероятных чатов (Predictive Prefetch):** заранее подгружает в память 1–2 наиболее вероятных следующих чата и превью свежих вложений, но *только* при хороших ресурсах (без перегрева и без забивания канала).
- **Упреждающая диагностика условий (Pre-flight Health Check):** заранее проверяет доступность нужного прокси/VPN, живость сессии аккаунта и доступность ПК-помощника, чтобы пользователь видел реальный статус канала **до** нажатия кнопки «Отправить».
- **План Б для маршрутов:** если основной прокси/маршрут деградирует (растёт пинг или пошли ошибки), движок заранее помечает запасной маршрут или переводит отправку в мягкую очередь с понятной подсказкой.
- **Жёсткий Backpressure (умение вовремя остановиться):** любая упреждающая задача немедленно ставится на паузу, если:
  - пользователь начал печатать, скроллить или открыл тяжёлое медиа;
  - батарея ниже 20% без зарядки;
  - включён режим экономии трафика (`saveData`) или медленная сеть;
  - мало свободной оперативной памяти;
  - внешний сервер вернул `429` / `503` с `Retry-After`.

### 4.3. Фаза «Сон, чтобы в будущем не уснуть» (Бюджет готовности)

Один активный мост (например, Telegram / WhatsApp / Discord) в реальных реализациях (вроде `mautrix`) может держать **50–200 МБ ОЗУ в простое** на аккаунт. Если держать всё вечно «разогретым» и одновременно копить мусор в памяти, мессенджер начнёт тормозить именно в нужный момент.

Поэтому у движка RatMes есть **автомат состояний бодрствования и сна**:

1. **`ACTIVE` (Активная работа):**
   - Пользователь общается прямо сейчас.
   - 100% приоритет отдаётся интерфейсу, вводу текста и срочной доставке сообщений.
   - Все фоновые тяжёлые задачи (упаковка, переиндексация, чистка) заморожены.

2. **`COOLING` (Остывание — например, 30–90 сек бездействия):**
   - Сброс накопившихся изменений в обычные файлы (`RatMes-Vault/`).
   - Лёгкий прогрев 1–2 чатов «на будущее» через `scheduler.postTask(..., { priority: 'background' })` / `requestIdleCallback`.

3. **`HOUSEKEEPING` (Тихое обслуживание — 2–5 мин бездействия):**
   - Дописывание человекочитаемых `.txt`-журналов и проверка целостности `outbox`.
   - Сброс декодированных картинок/видео и старых буферов из ОЗУ.
   - Компактизация локального индекса (WAL checkpoint) и обновление `memory.json`.
   - Перевод редко используемых или недоступных мостов (например, без VPN) в режим холодного ожидания.

4. **`DEEP_SLEEP` (Глубокий сон — >5 мин бездействия или свёрнутое окно):**
   - Минимальный пульс: остаётся только лёгкий слушатель входящих событий (push / long-poll / локальный сокет).
   - Потребление CPU стремится к 0%, память очищена, файлы уже в полном порядке на диске.
   - **Результат («не уснуть в будущем»):** когда пользователь резко возвращается или приходит волна сообщений с тяжёлыми файлами, RatMes просыпается мгновенно и **не тормозит**, потому что вся тяжёлая работа по сохранению и чистке уже была выполнена заранее во время покоя.

### 5.3. Паспорт условий каждого моста (Честный чек-лист)

Для каждого внешнего чата RatMes вычисляет состояние по 4 явным условиям:
- `account_linked`: подключён ли аккаунт в этом мессенджере;
- `agent_online`: запущен ли ПК-помощник (если мост требует ПК);
- `network_route_ok`: доступен ли канал напрямую (или поднят ли требуемый VPN/прокси для выбранной страны);
- `bridge_healthy`: нет ли бана, истёкшей сессии или временного `Retry-After`.

Если все 4 условия выполнены — статус **«Готов к отправке»** (зелёный).
Если не хватает хотя бы одного — RatMes **не молча падает**, а пишет точную причину (например: *«Telegram в профиле Россия требует активный VPN/прокси. Сообщение сохранено в локальную очередь и уйдёт сразу после включения маршрута»*).

## 6. Требования к скорости, надёжности и безопасности

- **Скорость UI:**
  - Холодный старт веб-клиента из кэша: < 300 мс.
  - Переключение между чатами: < 16 мс (виртуализация длинных списков сообщений).
  - Поиск по локальной истории: < 50 мс.
- **Безопасность и честность:**
  - Никакой скрытой телеметрии и отправки личных ключей на сторонние серверы.
  - Для каждого моста честно отображается уровень защиты: сквозное шифрование (E2EE) или транспортное шифрование (например, явная пометка об отсутствии E2EE у MAX и у обычных чатов Telegram).
  - Токены и ключи сессий мостов хранятся отдельно от папки читаемых переписок `RatMes-Vault/chats/`, с ограниченными правами доступа ОС (`0600`).
  - **Юридическая и техническая честность по мостам:** сторонние мессенджеры (WhatsApp, VK, WeChat, MAX и др.) могут ограничивать неофициальные клиенты по своим правилам (ToS). RatMes изначально проектируется модульно (архитектура адаптеров в духе `bridgev2`), с аккуратным соблюдением лимитов запросов и уважением `Retry-After`.

## 9. Глубокий разбор базы мессенджеров и базы движков (синтез для RatMes)

### 9.1. База темы мессенджеров: 6 главных архитектурных уроков

1. **TDLib (движок клиентов Telegram):**
   - Строится на **акторной модели** (нет общих мутабельных структур и тяжёлых блокировок — каждый домен вроде `MessagesManager`, `FilesManager`, `UpdatesManager` — отдельный актор с очередью сообщений).
   - **Трёхслойное хранение:** in-memory кэш → встроенный SQLite → транзакционный **binlog** (журнал для восстановления после падений и гарантированной досылки).
   - Жёсткое разделение внешнего API клиента и внутреннего протокола сети + движок закрытия «дыр» (`gap engine` по `pts/qts/seq`), чтобы сообщения всегда приходили в правильном порядке.
   - *Что берём в RatMes:* трёхслойность (`ОЗУ-кэш` → `SQLite WAL` → `обычные файлы RatMes-Vault + binlog/outbox`) и акторную изоляцию каждого моста.

2. **WhatsApp и Erlang/BEAM:**
   - Принцип **«пусть падает» (`let it crash`) + супервизоры**: если упало одно соединение/мост, падает только его изолированный актор, а супервизор мгновенно перезапускает его с экспоненциальной задержкой — остальной мессенджер даже не моргнул.
   - Умные редкие пинги простоя, батчинг статусов «печатает…» и ограничение частоты presence-событий, чтобы не жечь батарею и трафик на слабых сетях.
   - *Что берём в RatMes:* супервизор мостов (падение моста Discord или обрыв VPN Telegram никогда не вешает UI и не мешает чату VK или RatMes).

3. **Криптография: Signal Protocol (Double Ratchet + X3DH/PQXDH) и MLS (RFC 9420):**
   - **Double Ratchet** даёт новый ключ на каждое сообщение (Forward Secrecy) и «самолечение» после компрометации (Post-Compromise Security) для 1-на-1 чатов, плюс хранит ограниченный буфер пропущенных ключей для сообщений, пришедших не по порядку.
   - **MLS (RFC 9420, TreeKEM)** решает проблему групп и мульти-устройств за `O(log N)` вместо `O(N)` попарных шифрований (для группы из 1000 человек или 5 устройств у каждого — на порядки быстрее и легче).
   - *Что берём в RatMes:* для собственных чатов **RatMes ↔ RatMes** закладываем современный стандарт **MLS (RFC 9420)** (единый движок и для 1-на-1 с несколькими устройствами, и для групп) или Double Ratchet для 1-на-1 + MLS для групп.

4. **Устойчивость к отключениям и цензуре (Briar, SimpleX):**
   - **Briar** показывает, как работать вообще без интернета и без центральных серверов: локальная синхронизация по Wi-Fi/Bluetooth, очереди доставки и устойчивость при блэкаутах.
   - **SimpleX** показывает, как убрать центральный граф контактов: вместо «аккаунт → сервер» используются **однонаправленные очереди сообщений** на независимых ретрансляторах.
   - *Что берём в RatMes:* для собственных чатов RatMes — поддержка **LAN/Wi-Fi прямой доставки** без интернета + возможность подключать свой/независимый ретранслятор с минимальными метаданными.

5. **Мосты (Matrix / mautrix `bridgev2` / Beeper):**
   - Главный принцип `bridgev2` — **единый контракт коннектора** (подключение, логин, сопоставление чатов/сообщений/ответов, обратное сопоставление ID, медиа, статусы доставки).
   - Реальная цена памяти: один живой мост держит **50–200 МБ ОЗУ в простое**, поэтому все 10+ мостов нельзя держать горячими одновременно — нужен менеджер сна и ленивого пробуждения.

6. **Локальная синхронизация (Offline-First vs Local-First, SQLite WAL, CRDT, HLC):**
   - **SQLite в режиме WAL (`PRAGMA journal_mode=WAL`)** обязателен: фоновый воркер пишет синхронизацию в `-wal`, пока UI читает основную БД без единой блокировки кадра (<5 мс).
   - Комбинация моделей слияния: **UUIDv7** (сортировка по времени создания) + **HLC (Hybrid Logical Clock)** для порядка метаданных + **CRDT** (или append-only события) для черновиков/списков + **tombstones** (мягкое удаление, чтобы удалённое не воскресало после офлайна).

### 9.2. База движков: какие паттерны делают движок RatMes неубиваемым

1. **Акторная модель + Супервизоры (BEAM / TDLib):**
   - Нет общих изменяемых объектов между подсистемами: Ядро, UI, Хранилище, Планировщик сна и каждый Мост общаются типизированными сообщениями.
   - Ошибка в одном мосту никогда не ломает запись файлов и не замораживает интерфейс.

2. **Асинхронные планировщики: Work-Stealing vs Thread-per-Core (`Tokio` / `epoll` / `io_uring`):**
   - Кооперативные async-движки (`Tokio`, JS Event Loop) имеют одну главную ловушку: **долгий синхронный кусок CPU-работы без `yield` / `.await` замораживает весь движок** и портит хвостовую задержку (tail latency).
   - Вывод для RatMes: вся тяжёлая работа (сжатие медиа, криптография, индексация поиска, массовый экспорт) обязана либо идти в выделенном worker-потоке/пуле блокирующих задач, либо дробиться на микро-шаги с постоянной уступкой управления (`yield`).

3. **Детерминированные снимки, фиксированный шаг и граф зависимостей (опыт нашего `pereplet-prototype` + `folder-os`):**
   - Из собственного **`pereplet-prototype`** репозитория берём три проверенные идеи:
     - *неизменяемые снимки состояния* и явный запрет конфликтующей записи в одно поле (`core.mjs`);
     - *аккумулятор времени с ограничением шагов за тик* (`clock.mjs`), чтобы после долгой паузы/сна движок не завис, пытаясь «догнать всё за одну миллисекунду»;
     - *топологическая сортировка задач по зависимостям (DAG)* (`scheduler.mjs`), чтобы задачи фазы `HOUSEKEEPING` (сброс файлов → проверка хэшей → checkpoint SQLite → очистка кэша → сон) всегда шли в строгом, проверяемом порядке без циклов.
   - Из **`folder-os`** берём прозрачность файловой модели: ключевое состояние (`outbox`, `chats`, `memory`, `bridges/status`) можно читать и диагностировать как обычные файлы.

4. **Движок кэширования нового поколения — `S3-FIFO` (вместо наивного LRU):**
   - По крупным исследованиям кэшей (CMU, 2023–2024), большинство объектов в реальных нагрузках — **«однодневки» (one-hit wonders)**: ты один раз пролистал картинку или чужой канал и больше к ней не вернёшься. Обычный LRU тратит на них драгоценную ОЗУ, вытесняя реально нужные чаты.
   - **S3-FIFO** использует 3 простые статические FIFO-очереди (маленькую входную очередь `S` для быстрого отсева однодневок, основную `M` и призрачную `G` для запоминания недавно вытесненных ключей): проще, быстрее, без тяжёлых блокировок и даёт меньший процент промахов, чем классический LRU.
   - *Что берём в RatMes:* именно `S3-FIFO` для кэша медиа-превью и распарсенных страниц переписки в ОЗУ — случайный скролл ленты никогда не вымоет из памяти твои 5 главных чатов.

5. **Движок «Прошлое + Будущее + Сон» как единая система бюджетов:**
   - **Прошлое:** лёгкая матрица переходов Маркова (кто за кем открывается) + статистика отказов каналов + `G`-очередь S3-FIFO (что недавно вытеснили, но оно снова понадобилось).
   - **Будущее:** спекулятивный прогрев строго по бюджету (CPU, сеть, батарея) + предварительная проверка 4 условий моста.
   - **Сон:** 4 состояния (`ACTIVE → COOLING → HOUSEKEEPING → DEEP_SLEEP`), слияние таймеров (не дёргать процессор десятком мелких таймеров каждую секунду, а будить движок редкими сгруппированными импульсами) и гибернация холодных мостов.

### 10.2. Семь прикладных веток `RatMes Engine` (`RatMes.engine.*`)

Поверх фундамента `RatCore-App` строятся **7 специализированных веток мессенджера**. Каждая ветка обязана соблюдать **единый контракт `RatCore`**:
- общий формат вызова `(args, ctx)` с `traceId`, `agentId` и `dryRun`;
- общий формат ответа `{ ok, tool, data, error, tick, costMs, traceId }`;
- автоматическое логирование и проверяемость в headless Node.js.

1. **`msg.*` — Конвейер сообщений, `Outbox` и `Gap Engine`**
   - Единая каноническая модель сообщения: `UUIDv7` (порядок по времени) + гибридные логические часы `HLC` + статусы (`local → queued → sending → sent → delivered → read / failed`) + мягкое удаление (`tombstones`).
   - **Transactional Outbox:** нажатие «Отправить» сначала фиксируется локально (< 5 мс) и сразу отображается в интерфейсе, а сеть доставляет асинхронно с гарантией идемпотентности (никаких дублей при обрыве).
   - **Движок закрытия «дыр» (`Gap Engine`):** отслеживает курсоры `seq/pts` по каждому чату и каждому мосту; при разрыве последовательности автоматически запрашивает недостающий диапазон.
   - Поддержка собственных чатов **`RatMes ↔ RatMes`** (E2EE по MLS RFC 9420 / Double Ratchet + локальный Wi-Fi/LAN-режим без интернета) и унифицированный поток для всех внешних мостов.

2. **`vault.*` — Вечный файловый резерв `RatMes-Vault/`**
   - Гарантирует главное требование владельца: все чаты и вложения всегда лежат в обычных папках на диске (`.jsonl` — машинный лог, `.txt` — читаемая человеком переписка, `media/` — файлы вложений) и открываются без RatMes.
   - **Атомарная запись без потерь:** `tmp → fsync(tmp) → close → rename → fsync(parent_dir)` для снапшотов/метаданных + append-only `.jsonl` с автоматической обрезкой и самолечением битого хвоста после отключения питания.
   - **Быстрый индекс SQLite WAL (`PRAGMA journal_mode=WAL`):** UI читает ленту за < 5 мс без блокировок, пока фон пишет синхронизацию; при повреждении базы SQLite целиком пересобирается из `RatMes-Vault/`.
   - Стыкуется с `RatCore.tools.save` (контрольные суммы и миграции) и `RatCore.tools.stream` (опциональная упаковка холодных архивов `Deflate`).

3. **`chrono.*` — Трёхфазный движок времени («Прошлое + Будущее + Сон»)**
   - **Прошлое (`chrono.past`):** компактная матрица переходов Маркова (какие чаты открываются следом и в какой час дня), журнал здоровья маршрутов/мостов (таймауты, `429`, скачки пинга), призрачная очередь `G` кэша **`S3-FIFO`** (отсекает одноразовые картинки/каналы от действительно горячих чатов).
   - **Будущее (`chrono.future`):** спекулятивный прогрев в свободные миллисекунды (`scheduler.postTask` / `requestIdleCallback`) — держит топ-3 вероятных чата в ярусе `HOT`, делает предполётную проверку 4 условий моста (сеть → маршрут/VPN → статус аккаунта → очередь), но мгновенно отступает по **`Backpressure`** (батарея < 20 %, `saveData`, потолок ОЗУ, `Retry-After`).
   - **Сон (`chrono.sleep`):** 4 состояния **`ACTIVE → COOLING → HOUSEKEEPING → DEEP_SLEEP`**.
     - В `HOUSEKEEPING` задачи идут по строгому графу зависимостей (DAG без циклов): сброс буферов → сверка `.txt`-копий → `WAL checkpoint` → очистка временных файлов → пересчёт `S3-FIFO`.
     - В `DEEP_SLEEP` включается **слияние таймеров (Timer Coalescing)**, а редкие мосты сворачиваются до **64-байтной микросводки** (прямое применение `RatCore.tools.stream.sleepRegion`!).
     - При пробуждении ограничитель `maxSteps` из `RatCore` (`clock.js`) не даёт догону заморозить интерфейс.

4. **`route.*` — Профили стран (`RU` + весь мир) и маршрутизатор с «Планом Б»**
   - Встроенная таблица профилей стран с мгновенным переключением (`RU` по умолчанию, плюс пресеты для `EU`, `US`, `TR`, `CN`, `IR`, `AE`, `JP`, `KR`, `VN` и др.).
   - Для `RU` (реалии 2026): **VK** и **MAX** — прямой маршрут (с явным маркером отсутствия E2EE у MAX); **Telegram, WhatsApp, Discord, Viber, Signal** — раздельный VPN/прокси-контур на каждый мост + предварительная проверка статуса аккаунта.
   - Автоматический **План Б**: при деградации основного прокси/туннеля (рост задержек или серия ошибок) маршрут плавно переводится на резервный узел или ставит исходящие в спокойное ожидание в `Outbox` с понятной диагностикой.

5. **`connect.*` — Изолированные акторы-мосты (`Let it crash` + `Lazy Wake`)**
   - Единый интерфейс для всех сетей (собственный `RatMes`, VK, MAX, Telegram, WhatsApp, Discord, Viber, Signal, WeChat, LINE, KakaoTalk и др.): `auth`, `sync`, `send`, `edit`, `react`, `media`, `presence`, `hibernate`, `wake`.
   - **Изоляция супервизором (уроки Erlang/BEAM и TDLib):** каждый мост работает в своём изолированном контуре. Если упал Discord или отвалился Telegram — VK, родные чаты RatMes и запись в `RatMes-Vault/` продолжают работать без единого сбоя.
   - **Гибернация (`Lazy Wake`):** один живой мост держит 50–200 МБ ОЗУ, поэтому одновременно горячими держатся только активно используемые мосты; остальные спят и просыпаются либо по клику, либо по редким окнам опроса.

6. **`crypto.*` — Закрытый контур безопасности (`MessageGuard` + `SecretVault`)**
   - Прямое прикладное развитие 5-барьерного `ToolGuard` + `AssetVault` из `RatCore` (подробно — в §10.3).
   - Управляет ключами **MLS (RFC 9420)** / **Double Ratchet** для чатов `RatMes ↔ RatMes` и сессионными токенами всех внешних мостов.
   - Тяжёлые крипто-операции выполняются в фоновом потоке через транспорт `worker` (`RatCore.tools.bridge`) с zero-copy `Transferable ArrayBuffer`.

7. **`presence.*` — Тихие «живые» сигналы**
   - Склеивание событий «печатает…» (не чаще 1 пакета в 3–5 с), полное глушение фонового «онлайн» в фазах `COOLING`/`DEEP_SLEEP`, умное группирование уведомлений (анти-шторм при выходе из офлайна).

### 10.3. Как 5 барьеров `ToolGuard` из `RatCore` превращаются в `MessageGuard + SecretVault`

В `RatCore` 5 барьеров защищают движок от «сырых» мешей и битых вершин. В `RatMes Engine` **тот же самый инженерный механизм** защищает самое ценное в мессенджере — **ключи, сессии и сохранность переписок**:

1. **Барьер 1 — Одноразовая печать (`Provenance Seal` + `claimCryptoAuthority`):** подписывать исходящие конверты, сессии мостов и записи в `RatMes-Vault/` могут только официальные фабрики `RatMes.engine.{crypto,msg,vault}`.
2. **Барьер 2 — Закрытое хранилище `SecretVault` (аналог `AssetVault`):** UI, плагины, темы и внешние ИИ **никогда не видят сырых приватных ключей E2EE, куки WhatsApp или токенов Telegram/VK**. Наружу выдаются только замороженные непрозрачные хэндлы (`SessionHandle`, `KeyHandle`, `AttachmentHandle`), которые невозможно изменить извне.
3. **Барьер 3 — Запрет обхода конвейера (`Outbox-First` & `Atomic-Vault-Only`):** любая попытка записать файл в `RatMes-Vault/` напрямую (минуя `tmp → fsync → rename`) или протолкнуть отправку в сеть мимо `Outbox` и проверки `route.*` отклоняется с кодом `RM-101` / `RM-103` и пишется в журнал аудита.
4. **Барьер 4 — Статический аудитор (наследует `code-auditor` из `RatCore`):** проверяет код плагинов и UI на прямую работу с `fs.writeFileSync` по каталогу хранилища или прямое чтение секретов в обход шлюза (`RM-107`).
5. **Барьер 5 — Самодокументирующийся шлюз (`help()` + понятные ошибки):** каждая ошибка `RM-*` возвращает не сухой стектрейс, а ясный код, причину и подсказку (для пользователя — человеческую, для ИИ-агента — структурированную).

### 10.4. Как 5 транспортов `ratcore-bridge/1` связывают всё приложение целиком

Протокол `ratcore-bridge/1` (`ratcore/BRIDGE.md`) идеально закрывает гибридную архитектуру **Браузер/PWA + ПК-агент `RatMes Agent`** без изобретения новых протоколов:

| Транспорт `RatCore` | Роль в `RatMes Engine` | Что по нему ходит |
|---|---|---|
| **`inproc`** (0 мс) | Внутри процесса ПК-агента и внутри вкладки | Команды между `msg`, `chrono`, `vault`, `route` и локальным кэшем `S3-FIFO`. |
| **`worker`** (zero-copy `ArrayBuffer`) | Главный поток ↔ фоновые воркеры | Шифрование `crypto.*`, сжатие медиа/архивов `stream.*`, полнотекстовый поиск — 0 фризов UI. |
| **`broadcast`** (`BroadcastChannel`) | Синхронизация нескольких вкладок браузера | Прочитал чат во вкладке 1 → мгновенно обнулился бейдж во вкладках 2 и 3 без сервера. |
| **`ws`** (локальный `127.0.0.1`) | Браузер/PWA ↔ ПК-агент `RatMes Agent` | Живой поток событий от мостов VK/MAX/TG/WA/Discord, запись в `RatMes-Vault/`, сверка `stateHash` (`F-47`). |
| **`file`** (`comms/bridges/<peerId>/`) | Аварийный и межъязыковой канал без портов | Подключение внешних мостов (на Python/Go/Rust) или локальных ИИ-помощников через файловый обмен при полной изоляции сети. |

### 10.5. Совместимая система кодов ошибок (`RC-*` + `RM-*`)

`RatMes Engine` не ломает нумерацию `RatCore`: системные сбои нижнего ядра приходят с кодами **`RC-100..999`**, а прикладные события мессенджера — в собственном пространстве **`RM-100..699`**:

| Диапазон | Категория `RatMes Engine` | Типовые коды |
|---|---|---|
| `RM-100..199` | `MessageGuard` и `SecretVault` | `RM-101` запись в `RatMes-Vault` в обход атомарного конвейера; `RM-102` попытка извлечь сырой ключ/токен; `RM-103` отправка в сеть мимо `Outbox`; `RM-107` нарушение статического аудита |
| `RM-200..299` | `RatMes-Vault/` и локальная БД | `RM-201` обнаружен и самовылечен битый хвост `.jsonl`; `RM-202` нет места/прав на диске; `RM-203` расхождение SQLite WAL и файлового архива (запущена автопересборка) |
| `RM-300..399` | Профили стран и маршруты | `RM-301` мессенджер требует VPN/прокси для выбранной страны (например, TG/WA/Discord в `RU`); `RM-302` основной маршрут деградировал (включён План Б); `RM-303` все каналы недоступны (сохранено в `Outbox`) |
| `RM-400..499` | Мосты и аккаунты | `RM-401` истекла сессия моста; `RM-402` ограничение/проверка аккаунта; `RM-403` мост упал и перезапущен супервизором; `RM-404` получен `429 Rate Limit` (включён `Backpressure`) |
| `RM-500..599` | Движок времени (`chrono.*`) | `RM-501` прогрев «Будущего» отменён по `Backpressure`; `RM-502` долгий сон → догон разбит на порции через `maxSteps` |
| `RM-600..699` | Шифрование и `Gap Engine` | `RM-601` обнаружена дыра `seq` (запрошен догон); `RM-602` ошибка проверки подписи MLS/Double Ratchet; `RM-603` предупреждение об отсутствии E2EE на внешнем мосту (например, MAX) |

### 10.6. Как одно сообщение проходит всю связку `RatCore + RatMes Engine`

Пример: пользователь в России (`RU`) пишет «Привет, ты где?» в чат Telegram и нажимает Enter.
1. **Мгновенный локальный коммит (< 5 мс):** `RatCore.tools.input` фиксирует ввод → `RatMes.msg` выдаёт `UUIDv7` + `HLC` → `RatMes.vault` атомарно дописывает строку в `RatMes-Vault/` (`.jsonl` + `.txt`), индекс SQLite WAL и `Outbox`. Пользователь видит своё сообщение на экране **мгновенно**, даже без интернета.
2. **Доставка агенту и соседним вкладкам:** `RatCore.tools.bridge` шлёт конверт `ratcore-bridge/1` по `ws` в локальный `RatMes Agent` и по `broadcast` в остальные вкладки браузера; сверяется `stateHash`.
3. **Предполётная проверка («Будущее» + `route.*`):** `RatMes.route` по профилю `RU` подставляет назначенный VPN/прокси-контур для Telegram; `RatMes.chrono.future` проверяет 4 условия (сеть → VPN → валидность `SessionHandle` в `SecretVault` → нет `429`).
4. **Изолированная отправка (`connect.*`):** актор-мост Telegram (горячий или разбуженный через `Lazy Wake`) отправляет пакет под защитой супервизора. Если VPN просел — событие записывается в «Прошлое» (`chrono.past`), включается запасной маршрут или спокойное ожидание в `Outbox`, при этом VK, родные чаты RatMes и файловый архив не тормозят ни на миллисекунду.
5. **Фиксация и уход в «Сон»:** приходит `serverSeq` → `Gap Engine` подтверждает непрерывность → `RatCore.tools.watch` обновляет UI → `RatCore.tools.audio` играет лёгкий процедурный щелчок. Через 60 с бездействия `chrono.sleep` переводит движок в `COOLING` → `HOUSEKEEPING` (DAG-уборка и `WAL checkpoint`) → `DEEP_SLEEP` (слияние таймеров и сворачивание редких мостов в 64-байтную сводку по схеме `RatCore.stream.sleepRegion`).

### 10.7. Согласование с командой `RatCore` (`ratcore/comms/` RFC после слияния PR #250)

Чтобы не создавать конфликтов слияния с открытой веткой `arena/5b278e22-games` (PR #250), файлы внутри `ratcore/` на текущей ветке не изменяются. После слияния PR #250 в `main` архитектор `RatMes` (`ai-ratmes-architect`) регистрируется в `ratcore/comms/registry/agents.json` и оставляет для `ai-architect-01` в `ratcore/comms/channels/general/` короткий запрос на **2 точечные точки расширения** (без утяжеления игрового `RatCore`):
1. **Профиль сборки `RatCore.createAppCore()`** — лёгкий конструктор ядра, загружающий только 10 системных веток без 3D-рендеров, физики, анимации и воксельного мира.
2. **Хук `ToolGuard.registerDomainGuard(prefix, rules)`** — официальный способ для прикладного движка (`RM-*`) подключить свой закрытый контур (`MessageGuard` + `SecretVault`) поверх единого механизма `Provenance Seal` и общего журнала аудита.

## 11. Собственные инструменты `RatMes.tools.*` и закон «Вся передача через инструменты»

Полный справочник всех **12 собственных веток инструментов `RatMes Engine`** и **5 барьеров `TransferGuard`** вынесен в отдельный документ (по аналогии с `ratcore/TOOLS.md`):  
**→ [`docs/ratmes-tools.md`](./ratmes-tools.md)**

### Краткая суть (для целостности ТЗ)
- **Принцип `TransferGuard`:** как `RatCore` запрещает создавать сырые 3D-меши в обход `tools.build.*`, так **`RatMes Engine` запрещает любую «сырую» передачу данных** (прямой `fetch`, `WebSocket.send`, запись мимо `RatMes-Vault/` или отправку мимо `Outbox`, коды `RM-101..107`).
- **Все 6 видов передачи идут по одному инструментальному конвейеру:**
  1. Собеседнику в свой чат `RatMes ↔ RatMes` (`pack.*` → `vault.*` → `transfer.*` → `crypto.*`).
  2. Во внешние мессенджеры VK / MAX / Telegram / WhatsApp / Discord / Viber / Signal и др. (`pack.*` → `vault.*` → `transfer.*` → `route.*` → `connect.*`).
  3. Большие файлы и видео с нарезкой на чанки и автодокачкой при обрыве VPN (`pack.media` → `transfer.streamChunk`).
  4. Обмен между браузером (PWA), ПК-агентом `RatMes Agent`, вкладками, воркерами и базовым `RatCore` (`relay.*` поверх `ratcore-bridge/1`).
  5. Прямая передача без интернета по Wi-Fi / LAN (`relay.lanDiscover` → `relay.lanSend`).
  6. Перенос резервного архива `RatMes-Vault/` на новое устройство (`pack.bundle` → `transfer.streamChunk` → `vault.rebuildIndex`).
- **12 веток `RatMes.tools.*`:**
  - *Передача (4):* `pack.*`, `transfer.*`, `relay.*`, `gap.*`;
  - *Файлы и безопасность (2):* `vault.*`, `crypto.*`;
  - *Страны и мосты (2):* `route.*`, `connect.*`;
  - *Время, память, сигналы, самодиагностика (4):* `chrono.*`, `cache.*`, `presence.*`, `diag.*`.
